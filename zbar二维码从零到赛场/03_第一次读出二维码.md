### 核心就这 4 行

```python
from PIL import Image                  # ① 把图片文件打开成"图片对象"
from pyzbar.pyzbar import decode       # ② 在图片里找码并翻译成文字

img = Image.open("assets/01_clean.png")   # ③ 打开一张图
results = decode(img)                     # ④ 让 zbar 读它
```

### 逐行批注

**① `from PIL import Image`**
PIL（Pillow）负责"把磁盘上的 PNG 文件变成内存里的像素矩阵"。
为什么不直接用 OpenCV 的 `cv2.imread`？**两个都可以**，练习 3-D 会让你验证。
PIL 的好处是：路径里有中文也不会出问题（`cv2.imread` 在中文路径下会返回 `None`，
这是个非常著名的坑，第 06 课会再说一次）。

**② `from pyzbar.pyzbar import decode`**
注意 import 路径是 `pyzbar.pyzbar`，**两次 pyzbar**。
这是 Python 包的老式布局：外层是包名，里层是模块名。写成 `from pyzbar import decode` 也能用。

**③ `Image.open(...)`**
**只打开文件，不做任何处理。** 不转灰度、不缩放、不二值化 —— 这些活 zbar 自己会干。
（很多人一上来就手动 `convert("L")`，其实没必要；第 07 课会告诉你什么时候才需要手动干预。）

**④ `results = decode(img)`**
这一行把控制权交给 zbar。它内部做的事，用第 01 课的语言说就是：
**找三个定位图案 → 算出网格 → 采样每个格的黑白 → 解出比特 → 纠错 → 还原字符串。**

### 参考结果（第 1 步的完整输出）

```
==============================================================
第 1 步：最小可运行版本（4 行）
==============================================================
decode() 返回的是： <class 'list'>
返回内容： [Decoded(data=b'156+123+516+231', type='QRCODE', rect=Rect(left=40, top=40, width=210, height=210), polygon=[Point(x=40, y=40), Point(x=40, y=250), Point(x=250, y=250), Point(x=250, y=40)], quality=1, orientation='UP')]
里面第一个元素的类型是： <class 'pyzbar.pyzbar.Decoded'>
它带着的原始字节是： b'156+123+516+231'
→ 用 .decode() 转成人类看的字符串： 156+123+516+231
```

**三个必须看懂的点**：

| 观察 | 含义 |
|------|------|
| `type(results)` 是 `list` | **一张图里可能有多个码**，所以永远返回列表，哪怕只有一个 |
| `results[0].data` 是 `b'156+...'` | 前面那个 `b` 表示**字节串（bytes）**，不是文字。要 `.decode()` 才变成 `str` |
| 列表里只有一个元素 | 因为 `01_clean.png` 里只有一个码；一张图里没有码时返回 **`[]`（空列表）** |

> **批注：为什么是 `bytes` 而不是 `str`？**
> 因为二维码里存的本来就是**一堆字节**，标准并不要求它是文字。
> 你可以把一张小图片、一个压缩包塞进二维码（容量够的话）。
> zbar 只负责把字节还原出来，**它不知道也不关心这是不是人能读的**。
> 这也是为什么读到中文时经常需要 `data.decode('utf-8')` 而不是裸 `.decode()` ——
> 裸 `.decode()` 用的是 utf-8，万一码里是 GBK 编码的中文就会报
> `UnicodeDecodeError`。赛题里的任务码全是 ASCII（数字和 `+`），不会踩这个坑。

> **那个 `quality=1` 是什么？**
> zbar 给的"质量分"，干净清晰的图是 1。它只是一个参考值，**不要拿它当判据**：
> 有些糊图也能读到，quality 依然是 1。第 05 课会逐个字段拆开讲。

## 3. 动手 2：把"读码"包成函数，然后批量体检

单张能读不算本事。真正的工程问题是：**这批图里哪些能读、哪些不能、为什么？**

看脚本里的函数：

```python
def read_qr(path):
    """读一张图里的第一个二维码。读到返回字符串，读不到返回 None。"""
    img = Image.open(path)
    found = decode(img)
    if not found:                       # 空列表 = 一个码都没找到
        return None
    return found[0].data.decode()
```

**两个设计决定，都是刻意做的**：

1. **读不到返回 `None`，而不是抛异常**
   为什么？因为"读不到"在真实场景里**不是异常，是常态**。
   摄像头 30fps，一秒里 29 帧读不到都很正常，程序不能因此崩掉。
   用 `None` 让调用方自己决定："跳过这帧" 还是 "再试一次"。
2. **只返回第一个**
   因为大多数场景（比如赛场上的任务码板）只有一个码。
   需要多个时再写别的函数（练习 3-C）。

> **批注：`if not found:` 为什么能判断空列表？**
> Python 里空列表、空字符串、`None`、`0` 都算"假"（falsy）。
> 所以 `if not found` 等价于 `if len(found) == 0`，但更短。
> 这是 Python 里非常地道的写法。

### 把这张表读成三条结论

**结论 1：旋转完全不是问题。**
`10_rot10/15/30/45/90/180` 全部 OK。这正是第 01 课说的"三个定位图案的作用"：
它让 zbar 能自己算出方向，**不需要你把码摆正**。

**结论 2：尺寸有个断崖。**
`03_size_40` 能读、`03_size_30` 不能。换算成第 01 课的语言：

| 图 | 整图边长 | 每格像素（29 格） | 能读 |
|----|---------|------------------|------|
| `03_size_400.png` | 400px | 13.79 px/格 | ✅ |
| `03_size_200.png` | 200px | 6.90 px/格 | ✅ |
| `03_size_120.png` | 120px | 4.14 px/格 | ✅ |
| `03_size_80.png` | 80px | 2.76 px/格 | ✅ |
| `03_size_60.png` | 60px | 2.07 px/格 | ✅ |
| `03_size_40.png` | 40px | **1.38 px/格** | ✅ |
| `03_size_30.png` | 30px | **1.03 px/格** | ❌ |

> **⚠️ 这里有个重要提醒：不要背"每格至少 3 像素"这个数字。**
> 第 01 课我说工程经验是 3~4 像素/格。但**你看实测：1.38 像素/格也读出来了**。
> 为什么？因为这张图是**完美合成的**：没有噪声、没有模糊、没有光照不均。
> 在这种理想条件下 zbar 的采样精度足够。
>
> 真实摄像头画面里（第 09 课会测），1 像素/格绝对读不出。
> **所以正确的理解是**：像素/格只是"预算"的一部分，
> 另一半是"图像有多干净"。**两个因素一起决定成败，不能单独拿一个数字当铁律。**
> 这就是为什么第 09 课要做"压力测试"—— 把变量一个个拆开测。

**结论 3：噪声、眩光、遮挡是"结构性"失败。**
`06_noise`、`08_glare`、`09_occluded` 三张失败。
注意它们失败的**性质**不同：

- `06_noise`（椒盐噪声）：**能救**。第 07 课用中值滤波就能救活。
- `08_glare`（反光斑）：**很难救**。光斑把格子的黑白关系彻底洗白了，信息没了。
- `09_occluded`（局部涂白）：**分情况**。涂掉的部分如果落在纠错能力范围内能救，超了就废。

> 这三张图先埋在这里，**第 07 课我们拿九种药方逐个抢救它们**。现在先记住结论：
> **能救的失败和不能救的失败，是两种东西。** 工程上要分清，不然会白花力气。

### 参考结果

```

第 3 步：喂一张没有码的图（体会『失败』长什么样）
==============================================================
decode(白底黑方块图) 返回： []
len(返回值) = 0   ← 0 表示列表是空的，不是报错
read_qr(同一个文件) 返回： None
```

**这一小步的价值在于建立一个正确的心智模型**：

> **"读不到" = 返回空列表，不是报错、不是崩溃、不是异常。**

所以你的代码里**永远不需要** `try: ... except` 来处理"这张图没码"。
只有"图片文件根本打不开"（`FileNotFoundError`）才需要 try。

> **批注：为什么这个设计很关键？**
> 想象你的机器人以 30fps 跑 3 分钟 = 5400 帧。
> 如果"没读到"要抛异常，你要写 5400 次异常处理，而且异常在 Python 里很慢（微秒级开销）。
> zbar 选了"返回空列表"这条路，让常态变得便宜。
> **设计 API 时，"常态"要便宜，"异常"才用异常。** 这是个很值得学的设计经验。

**这两行的意义，比它们看起来大得多。**

**如果 `decode()` 需要"码铺满图片"，本教程第 5 章以后就全都写不下去了。**
它不需要 —— 因为 zbar 是**扫描式**找码：先找定位图案，再顺着算网格。
它天生就是"在一张大图里找小码"。

> **批注：这是"知道原理"带来的确定感。**
> 如果你只会背 API，你会担心"码太小怎么办"，然后去写一堆手工裁剪代码。
> 如果你知道 zbar 靠定位图案扫描，你就会先问："**定位图案还完整吗？**"
> —— 这才是该问的问题。
> 第 09 课的压力测试就是围绕这个问题设计的：多大的码，定位图案才还"看得见"。

> **为什么 `20_before_after.png` 是 3 个？**
> 那是第 07 课要用的"修复前后对比图"，一张图里并排放了 **4 组共 8 张小图**
> （噪声原图/中值后、低对比度原图/CLAHE 后、眩光原图/处理后、30px 原图/放大后）。
> 8 张里只有 3 张真的能读出码 —— 这和前面的结论完全对得上：
>
> | 面板 | 能读吗 | 对应结论 |
> |------|-------|---------|
> | 椒盐噪声**处理后**（中值） | ✅ | 噪声能救 |
> | 低对比度**原图** | ✅ | 这张本来就勉强能读 |
> | 低对比度 **CLAHE 后** | ✅ | 增强后更稳 |
> | 噪声原图 / 眩光原图 / 眩光处理后 / 30px 原图 / 30px 放大后 | ❌ | 眩光救不回来 |
>
> 顺手说明了两件事：**`decode()` 会把一张图里所有码都找出来**；
> 而且**返回顺序不保证**是"从左到右"，你要自己按 `rect.left` 排序（第 05 课会做）。

```python
    page.paste(one, (x, 10))
```

**3-D**

```python
import cv2
from pyzbar.pyzbar import decode

img_bgr = cv2.imread("assets/01_clean.png")            # 注意是 BGR 顺序
gray = cv2.cvtColor(img_bgr, cv2.COLOR_BGR2GRAY)      # 转灰度
r = decode(gray)                                       # pyzbar 直接吃 numpy 数组
print(r[0].data.decode() if r else None)
```

参考结果：

```
156+123+516+231
```

**结论：两条路结果一致。** pyzbar 接受两种输入：
- PIL 的 `Image` 对象
- numpy 数组（**灰度或彩色都行**）

> **批注：为什么要专门提这个？**
> 因为**第 06 课开始处理摄像头画面，画面天生就是 numpy 数组**（`cap.read()` 返回 BGR 数组）。
> 所以你**不需要**把 numpy 数组转成 PIL 图再解码 —— 那是一次毫无意义的拷贝，
> 在 640×480 上大约浪费 1~2 ms，30fps 下白扔 5% 的算力。
> **少一次转换 = 多一帧余量。**

```
Traceback (most recent call last):
  ...
FileNotFoundError: [Errno 2] No such file or directory: 'assets/不存在.png'
```

**和"读不到"不同**：这是文件层面就失败了，**它确实抛异常**。
稳一点的写法：

```python
def read_qr_safe(path):
    try:
        return read_qr(path)
    except (FileNotFoundError, OSError):
        return None
```

> **分清两种失败**，这是本课最想让你带走的东西之一：
> | 失败类型 | 表现 | 该不该 try |
> |---------|------|-----------|
> | 文件打不开 | `FileNotFoundError` | **该** try |
> | 图里没码 | 返回 `[]` | **不该** try |
> | 图里有码但读不出 | 返回 `[]` | **不该** try（要靠预处理去救） |

## 7. 常见错误

| 报错 / 现象 | 原因 | 解法 |
|------------|------|------|
| `ImportError: Unable to find zbar shared library` | 没调 `zbar_bootstrap.ensure()` | 脚本开头加那两行（见第 02 课） |
| `FileNotFoundError` | 路径不对 / 没生成素材 | 先跑 `code/make_assets.py`；确认在教程根目录下运行 |
| `UnicodeDecodeError: 'utf-8' codec can't decode` | 码里存的不是 UTF-8 文字 | 试 `data.decode('gbk')`，或按字节处理 |
| `cv2.imread` 返回 `None` | 路径含中文（OpenCV 的老毛病） | 改用 PIL 读，或用 `cv2.imdecode(np.fromfile(...), ...)` |
| 明明图里有码，却返回 `[]` | 图太小 / 太糊 / 太暗 / 有眩光 | 第 07 课的九种药方 |
| 读到的是 1 个，但你想要第 2 个 | 一张图多个码 | `results[1]`，或先按 `rect.left` 排序 |

## 8. 自测题

1. `decode()` 的返回值类型是什么？为什么不是直接返回 `str`？
2. 图里没有二维码时，`decode()` 返回什么？会抛异常吗？
3. `d.data` 和 `d.data.decode()` 有什么区别？
4. 为什么 `03_size_40.png`（1.38 像素/格）能读，而真实摄像头画面里这个密度读不到？
5. `20_before_after.png` 里有几个码能被解出来？返回列表的顺序按什么排？你怎么让它稳定？
6. `cv2.imread` 读中文路径会怎样？怎么绕过？

<details>
<summary>参考答案</summary>

1. `list`，元素是 `pyzbar.pyzbar.Decoded`。因为一张图里可能有多码，且码里存的是**字节**而非必然是文字。
2. 返回 `[]`（空列表），**不抛异常**。"没码"是常态，不是异常。
3. `d.data` 是 `bytes`（原始字节，如 `b'156+...'`）；`.decode()` 按 UTF-8 变成 `str`。
4. 合成图完美无噪无模糊；真实画面有噪声、模糊、光照不均、压缩失真，同一密度下采样误差大得多。像素密度只是因素之一。
5. 3 个（8 个面板里只有 3 个能解）；顺序是 zbar 内部扫描顺序，不保证左右/上下；用 `sorted(results, key=lambda d: d.rect.left)` 排序。
6. 返回 `None`（不报错，静默失败，更坑）；改用 PIL 读，或 `cv2.imdecode(np.fromfile(path, dtype=np.uint8), cv2.IMREAD_COLOR)`。
</details>

## 9. 小结

| 你学到的 | 一句话 |
|---------|--------|
| 核心 API | `decode(Image.open(path))` → 列表 |
| 失败的样子 | 读不到 → `[]`；文件错 → 异常。**两种要分清** |
| `bytes` vs `str` | `d.data` 是字节，`.decode()` 才变文字 |
| 旋转实测 | 0°~180° 全部能读（定位图案的功劳） |
| 尺寸实测 | 40px（1.38px/格）还能读，30px 崩了 —— 但这是"理想图"的结论 |
| 结构性失败 | 噪声能救、眩光难救、遮挡看程度 —— 第 07 课逐个救 |
| 多码 & 顺序 | 一张图可能多码，顺序不保证，要自己排序 |
