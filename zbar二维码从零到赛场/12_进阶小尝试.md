## A. 从码的大小反推距离 —— 不用激光测距

### A.1 原理：一张相似三角形

```
      物体（真实宽 W = 80mm）
      ├──────────┤
      ╲          ╱
       ╲        ╱          ← 光心
        ╲      ╱
         ╲    ╱
          ╲  ╱
           ╲╱
           ││  成像平面（宽 w 像素）
           ├┤
```

相似三角形给你一个比例关系：

```
w / f = W / d        移项：  d = f × W / w
```

- `W` = 码的真实宽度。**赛题给了：80mm（含边框）**
- `w` = 码在画面里的宽度（像素）。**zbar 的 `polygon` 直接给你**
- `f` = 焦距（单位是像素，不是毫米！）。**必须自己标定一次**

> **为什么 f 的单位是像素？** 因为 `w` 是像素。比例式两边单位要一致：
> `w(px) / f(px) = W(mm) / d(mm)`，像素约掉、毫米约掉，剩下无量纲，成立。
> **这是最容易被绕晕的地方**：明明叫"焦距"，却不是镜头上印的 3.6mm。

### A.2 标定：量一次，用一辈子

```python
# 标定：把 80mm 的板子放在你量得准的距离，读一次，算 f
w0 = 236.0        # 500mm 处，码在画面里 236px 宽
d0 = 500.0        # 这个距离用尺子量的
W  = 80.0         # 码的真实宽度（赛题规定）
f  = w0 * d0 / W  # 236 × 500 / 80 = 1475.0 px
```

**注意 f 依赖三件事**：镜头的物理焦距、传感器的像素密度、以及**你输出图像的分辨率**。
所以"换个分辨率（640×480 → 1280×720），f 就变了"，**必须重新标定**。

> **实操建议**：标定 3 次取平均，误差能到 5% 以内。
> 5% 的误差在 1.5m 处是 ±75mm —— 对"要不要再往前挪 100mm"这个决策**完全够用**。

**怎么用这张表**（结合第 09 课的实测）：

| 画面里的码宽 | 距离 | 第 09 课命中率 | 该做什么 |
|------------:|-----:|--------------:|---------|
| 40px（1.38px/格） | 2950mm | **0%** | 必须往前走 |
| 60px（2.07px/格） | 1967mm | 75% | 不太稳，再近点 |
| **80px（2.76px/格）** | **1475mm** | **100%** | **可以读** |
| 120px（4.14px/格） | 983mm | 100% | 很稳 |
| 400px（13.79px/格） | 295mm | 100% | 太近了，可能拍不全 |

于是你可以写出**真正的闭环控制**：

```python
text, level = reader.read(frame)
if text:
    w_px = poly_side_length(results[0].polygon)     # 第 05 课学的
    d_mm = 1475.0 * 80.0 / w_px
    if w_px < 80:
        go_forward(100)          # 太远，往前走 100mm 再读
    else:
        accept(text, d_mm)       # 够清楚了，认账，顺便记下距离
```

> **这就是"闭环"**：不是猜"应该够近了吧"，而是**量了再动**。
> 第 09 课那句"失败就挪 2mm 再读"，现在有了量化依据：
> 1px ≈ 1.0mm（在 1475mm 处、80px 码宽时），所以挪 20mm ≈ 码宽变化 1px。

### A.4 三个坑

1. **倾斜会让 w 变小** → 距离估算偏大。
   所以要用 `polygon` 的**最长边**，不是 `rect.width`（第 05 课实测：45° 时 rect 是 polygon 的 1.419 倍）。
2. **镜头畸变**：画面边缘的码会被拉长。近距（<500mm）用广角镜头时误差可达 10%。
   → 只在你**标定过的距离范围内**用这个公式。
3. **码板不是正对着你**（有俯仰角）→ W 投影变小 → 距离估大。
   → 这正是 D 节"找四个角"的用途：有了角点就能做透视校正，再量。

## B. 滑动窗口投票 —— 用时间换准确率

### B.1 第 10 课的"连续 2 次"不够用的时候

第 10 课的 `confirm=2` 要求**严格连续**：中间夹一帧读不到，从头数。

坏处：假设命中率只有 60%（第 06 课回放实测是 83.3%），
那么"连续 2 次"的成功概率 ≈ 0.6 × 0.6 = 36%，
而"3 帧里随便读到 2 次"的成功概率 ≈ 0.6³ + 3×0.6²×0.4 = **64.8%**。

**同样的帧、同样的码，宽容的规则把成功率从 36% 提到 65%。**

> 这就是"用时间换准确率"：你多等 1 帧，换来的是**大幅降低"等不到"的概率**。
> 停车读码可以慢慢等，所以这笔交易很划算。

### B.2 实现（严格过半，不是"最多票"）

```python
window = 5
buf = []
decided = None

for s in stream:
    if s:                                  # 没读到就不进窗口（不占票位）
        buf.append(s)
        buf = buf[-window:]                # 只保留最近 N 个
    if len(buf) >= (window + 1) // 2:      # 至少要有过半的样本才判
        top, n = Counter(buf).most_common(1)[0]
        if n * 2 > len(buf):               # ← 严格过半才认账
            decided = top
```

**两个细节决定成败**：

**① `if s:` —— 没读到的帧不进窗口。**
如果让 `None` 也占一个票位，那么"画面糊了 3 帧"就会把真实答案的票数比例压到一半以下。
**空白票不该算反对票。**

**② `n * 2 > len(buf)` —— 严格过半，不是"最多票"。**
如果用 `most_common(1)` 直接取最多票，那么窗口里有 3 个不同结果各 1 票时，
它会**随便挑一个**告诉你 —— 那不叫投票，那叫赌博。

> **写成 `n * 2 > len(buf)`** 而不是 `n / len(buf) > 0.5`，
> 是因为**避免浮点除法**。整数比较永远精确，`0.6666...` 永远有误差。

### B.3 实测输出

```bash

```

```

    第  1 帧：156+123+516+231
    第  2 帧：156+123+516+231
     ...
    第  5 帧：156+123+5l6+231      ← 误读（小写 L 混进数字）
    ...
    第  8 帧：999+999+999+999      ← 完全错误的码（读到了别的板子）
    ...
    第 11 帧：None                ← 这一帧没读到

    第  1 帧后：窗口=['156+123+516+231']  当前判定=None
    第  2 帧后：窗口=['156+123+516+231', '156+123+516+231']  当前判定=None

  最终判定：156+123+516+231
```

**三个误读全被压掉了**，而且判定在第 3 帧就出现（不是等到第 5 帧）——
因为代码里那句 `len(buf) >= (window + 1) // 2` 让它在"攒够一半样本"时就开始判。

### B.4 窗口大小怎么选（实测）

同一段 12 帧（含 2 个误读、1 个 None），换不同窗口：

| 窗口 N | 首次判定在第几帧 | 最终判定 | 误判帧数 |
|------:|----------------:|---------|--------:|
| 3 | **第 2 帧** | `156+123+516+231` | 0 |
| 5 | 第 3 帧 | `156+123+516+231` | 0 |
| 7 | 第 4 帧 | `156+123+516+231` | 0 |

**读法**：N 越大，判得越晚（多等 N/2 帧），但对"连续多次误读"的免疫力越强。
这段流里的误读是**孤立**的，所以三种窗口都扛住了。
真要看出差别，得让误读**连续出现 2~3 次** —— 那才是 N 的真正意义。

> **实战建议**：**N=3 或 5**。
> N=3 只多等 1 帧，能挡单帧误读；N=5 挡得更狠，代价是 2 帧延迟。
> **N=7 以上不推荐**：赛场上板子是静止的，你不需要这么长的窗口。

## C. 按毫米精确打印 A4 码板（可以直接上赛场）

### C.1 为什么这件事很难

要打一块"**80mm 见方**（含白边）的码，印在 A4 中间"，你需要精确控制三件事：

1. **每格多少像素** —— 决定清晰度
2. **每格多少毫米** —— 决定打出来是不是 80mm
3. **白边（安静区）够不够** —— 第 04 课实测：白边被深色物体吃掉就直接读不出

### C.2 算账

```
A4 = 210 × 297 mm，打印 300 DPI
  → 1mm = 300 / 25.4 = 11.811 px
  → 整页 = 210×11.811 = 2480 px 宽，297×11.811 = 3507 px 高

这个任务码是 version 1：数据区 21×21 格
  → 加四周各 4 格白边 = 21 + 8 = 29 格
  → 每格 = 80mm / 29 格 = 2.759 mm = 32.58 px
  → 成品正好 945px = 80.0mm 见方（不是"约 80mm"）
```

> **为什么是 version 1？** 因为 `156+123+516+231` 里的字符全在字母数字表
> （`0-9 A-Z $ % * + - . / :` 和空格）里，库会用 **alphanumeric 模式**，非常省空间。
> 15 个字符塞进 version 1 绰绰有余。
> **赛题送的这 80mm×80mm 尺寸，刚好够 version 1 的 29 格 × 2.76mm。**

### C.3 关键技巧：逐格画，不要"画小再放大"

```python
n = len(matrix)                      # 已含四周各 4 格白边 → 29
step = target_px / n                 # 945 / 29 = 32.586…
for r in range(n):
    for c in range(n):
        if matrix[r][c]:             # 只有黑格才画
            x0 = round(c * step); x1 = round((c + 1) * step)
            y0 = round(r * step); y1 = round((r + 1) * step)
            cv2.rectangle(page, (x0, y0), (x1, y1), (0, 0, 0), -1)
```

**为什么不能"先生成 29×29 的小图，再 resize 到 945×945"？**

因为 `resize` 会做插值，**边界的黑格会被平均成灰**。
而二维码的每个格**必须是纯黑或纯白** —— 灰边会让 zbar 的行列判定在两格之间摇摆。

> **这条和第 12 课 D 节"补白边 2x 双线性读不出"是同一个道理**：
> **几何图形在放大时，要"重新画"，不要"拉伸原图"**。
>
> **实测对照**（D 节表格）：补白边 + 双线性放大 → **读不出**；
> 补白边 + 最近邻放大 → 读得出。**插值方式能决定成败。**

### C.4 红线标注框：只能画在码外

```python
pad_mm = 5                                   # 距码边界 5mm
```

这张图上画了一个红色标注框，方便你打印后**用尺子量**。
但**它必须画在码外 5mm 处**：

> **实测教训**：第一版我把红线画在**码的边界上**，结果**直接读不出了** ——
> 因为红线正好覆盖掉了一圈白边（安静区），zbar 失去了判定边界的参照。
>
> **规则**：任何标注、边框、贴纸，都必须在**安静区之外**。
> 赛题要求"码四周留白"，本质就是这个原因。

### C.5 打印要点（四条，都写进脚本里了）

```
1) 打印机缩放必须选『100% / 实际大小』，不能选『适合页面』
   （选了会缩到 97%，80mm 变 77.6mm，A 节的距离估算就全错了）
2) 白纸黑墨，别用彩色；亚光纸 > 光面纸（反光是读码头号杀手）
3) 打出来用尺子量红色框：应该是 90mm（80 + 左右各 5mm）。
   不是就调 DPI 重打，别凑合
4) 贴板子时码四周至少留 10mm 白边 —— 第 04 课实测：
   白边被深色边框吃掉时，border=0 直接读不出
```

**验证**：`assets/30_print_board_a4.png` 用 zbar 读一遍 → `156+123+516+231` ✓

> **这个文件的用途不只是"好看"**：赛场上你的码板是主办方给的，
> 但**调试时你需要自己的码板**（尤其是"码板在场地边缘、斜着看"这种场景）。
> 自己打一块规格一致的板子，才能复现赛场的难度。

## D. OpenCV 找四个角 + 摆正 —— 给底盘对准，还能救"看见但读不出"

### D.1 zbar 给多边形，OpenCV 给四角 + 一张"摆正图"

```python
ok, pts, straight = cv2.QRCodeDetector().detectAndDecode(gray)
#   ok       解码出的字符串（可能为空）
#   pts      四个角点 (4,2) float32，顺序：左上/右上/右下/左下
#   straight 把码"摆正"后的二值点阵（21×21，每格 1 像素）
```

实测（`11_perspective.png`，一张故意做成透视歪斜的图）：

```
OpenCV 读到：'156+123+516+231'
四个角（顺序：左上/右上/右下/左下）：
  角1: (73.9, 46.9)
  角2: (237.4, 85.1)
  角3: (203.7, 241.5)
  角4: (40.2, 189.9)
中心点：(138.8, 140.8)
上边偏角：13.1°（0 = 码摆正；负数 = 画面里逆时针歪了）

zbar 也给了同样的信息，对比一下：
  zbar polygon：[(40, 190), (204, 242), (237, 85), (74, 47)]
```

**注意两边数值几乎一样（差 0.1~0.3px），但顺序不同**：

- OpenCV 保证"左上/右上/右下/左下"
- zbar 的 polygon **首点不一定是左上角**，也不保证方向

> **所以"取 polygon[0] 当左上角"是错的。** 要按"最接近 (min_x, min_y) 的那个点"来定位，
> 或者干脆用 OpenCV 的角点顺序。

### D.2 摆正再交给 zbar（救命的一招）

```python
def straight_to_zbar(gray, scale=8, border=4):
    _, _, st = cv2.QRCodeDetector().detectAndDecode(gray)
    if st is None or getattr(st, "size", 0) == 0:
        return None, "OpenCV 没检测到码"
    m = st[:, :, 0] if st.ndim == 3 else st
    m = (m > 127).astype(np.uint8) * 255          # 二值化：>127 → 255（白），否则 0
    m = np.pad(m, border, constant_values=255)    # 补 4 格白边
    m = cv2.resize(m, None, fx=scale, fy=scale,
                   interpolation=cv2.INTER_NEAREST)   # 放大，最近邻！
    r = decode(m)
    return (r[0].data.decode() if r else None), f"{m.shape[0]}×{m.shape[1]}"
```

实测：

```
  11_perspective.png     → 156+123+516+231      232×232
  13_scene.png           → 156+123+516+231      232×232
  10_rot45.png           → 156+123+516+231      232×232
  03_size_40.png         → None                 OpenCV 没检测到码
  08_glare.png           → None                 OpenCV 没检测到码
  09_occluded.png        → None                 OpenCV 没检测到码
```

**为什么前三个能救回来？** 因为它们"看得见但 zbar 自己读不出"（透视/旋转）。
摆正之后，码变成了**完美的正交点阵**，等于把难题化简成了送分题。

**为什么后三个救不回来？** 因为 OpenCV 自己都**检测不到** —— 信息已经不在画面里了。

> **一句话总结**：这条路救的是"**能看见但读不出**"，救不了"**根本找不到**"。
>
> 这也是为什么它是**兜底层**（第 10 课的 L10），不是主力。

### D.3 straight 到底需要什么？（逐条实测）

这张表是**自己动手测出来的**，比任何口诀都可靠：

| 输入 | 尺寸 | 每格像素 | 结果 |
|------|-----:|--------:|------|
| 裸码 1x | 21×21 | 1.00 | **读不出** |
| 裸码 2x（最近邻） | 42×42 | 2.00 | 读得出 |
| 补白边 1x | 29×29 | 1.00 | **读不出** |
| 补白边 2x（最近邻） | 58×58 | 2.00 | 读得出 |
| 补白边 2x（**双线性**） | 58×58 | 2.00 | **读不出** ← 边界被糊成灰 |
| 补白边 8x（最近邻） | 232×232 | 8.00 | 读得出 |

**两条硬要求**：

1. **每格 ≥2 像素**（1px/格 必失败，与第 09 课"≥2~3px/格才稳"一致）
2. **插值必须用最近邻**（`INTER_NEAREST`）—— 双线性会造出灰过渡带

> **注意一个反直觉之处**：裸码 2x **双线性** 读得出，补白边 2x 双线性**读不出**。
> 我推测是灰过渡带落在白边与码边界之间，干扰了静区判定（**未进一步验证**）。
> **工程做法**：既然最近邻在所有情况下都行，就**只用最近邻**，别去挑战它。

### D.4 机器人怎么用这四个角

| 数据 | 用途 | 怎么算 |
|------|------|--------|
| 中心点 | 底盘转向对准 | `((x1+x3)/2, (y1+y3)/2)` |
| 上边偏角 | 判断车是不是斜着停 | `atan2(y2-y1, x2-x1)` |
| 边长 | 测距（A 节） | 四边长取平均（透视下长边更可用） |
| 长/短边比 | 判断透视强度 | `max/min`；>1.1 就该先摆正 |

实测 `11_perspective.png`：最长边/最短边 = **1.170**（172.0/147.0）—— 明显透视。
而 `01_clean.png` 是 1.000，`13_scene.png` 是 1.025。

> **阈值建议**：长宽比 > 1.1 → 先做透视校正再算距离（否则 A 节的估算会偏大）。

```
  15_barcode_ean13.png       → EAN13    4006381333931
```

### E.1 判型：`.type` 字段

```python
results = decode(img)
for r in results:
    if r.type == "QRCODE":
        handle_qr(r.data)
    elif r.type in ("CODE128", "EAN13", "EAN8", "CODE39"):
        handle_barcode(r.data)
    else:
        print(f"没处理过的类型：{r.type}")
```

**为什么必须判型？** 因为智能分拣赛项的货物上**可能同时有二维码和条形码**，
两者承载的信息完全不同（二维码=身份，条形码=货号）。不判型就会把两种数据混在一起。

### E.2 一维码的几个特点（对比二维码）

| | 二维码 | 一维码 |
|---|-------|--------|
| 数据结构 | 二维网格 + 定位角 | 一排竖条 + 检查位 |
| 旋转容忍 | **任意角度**（自定位角） | 只能小角度倾斜（扫描线要横穿竖条） |
| 容量 | 大（最多几千字符） | 小（十几位） |
| `quality` 实测 | QR 恒为 **1** | CODE128 = **178**，EAN13 = **355** |
| polygon 点数 | 通常 4 个 | 可能 4 或 **5** 个 |

> **`quality` 不可比**！QR 的 1 和 EAN13 的 355 是两套完全不同的量纲
> （第 05 课就强调过）。**别用它做"清晰度阈值"。**

### 练习 12-B　窗口取 3 / 5 / 7 有什么差别

用 B 节那段 12 帧的模拟流，分别用 N=3、5、7 跑，记录"首次判定在第几帧"。

<details>
<summary>参考答案</summary>

```python
from collections import Counter
TC = "156+123+516+231"
stream = [TC, TC, "156+123+516+231", TC, "156+123+5l6+231", TC, TC,
          "999+999+999+999", TC, TC, None, TC]

for win in (3, 5, 7):
    buf, decided, first = [], None, None
    for i, s in enumerate(stream, 1):
        if s:
            buf.append(s); buf = buf[-win:]
        if len(buf) >= (win + 1) // 2:
            top, n = Counter(buf).most_common(1)[0]
            if n * 2 > len(buf):
                decided = top
                if first is None:
                    first = i
    print(f"  N={win}: 首次判定第 {first} 帧，最终={decided}")
```

**实测结果**：

| 窗口 N | 首次判定 | 最终判定 |
|------:|--------:|---------|
| 3 | **第 2 帧** | `156+123+516+231` |
| 5 | **第 3 帧** | `156+123+516+231` |
| 7 | **第 4 帧** | `156+123+516+231` |

**读法**：延迟大约是 `(N+1)//2` 帧。三种都能扛住**孤立**误读，
差别在于扛"连续误读"的能力 —— 这段流里没有连续误读，所以看不出差别
（**这就是实验设计的局限，第 09 课学过：结论要说明适用条件**）。

</details>

## H. 常见错误

| 现象 | 原因 | 修法 |
|------|------|------|
| 距离估算总偏大 | 用了 `rect.width`，倾斜时它比真实边长小 | 用 polygon 的**最长边** |
| 距离估算忽大忽小 | 标定距离处与使用距离差距太大 | 只在标定距离 ±50% 范围内用 |
| 投票总也判不出来 | 让 `None` 进了窗口占票位 | `if s:` 才 append |
| 投票选了错误答案 | 用了 `most_common(1)` 而不是严格过半 | `n * 2 > len(buf)` |
| 打印出来量着是 77.6mm | 打印对话框选了"适合页面" | 选 100%/实际大小 |
| 打印的码读不出 | 红线/边框压到了安静区 | 标注一律画在码外 ≥5mm |
| straight 放大后读不出 | 用了默认的双线性插值 | `interpolation=cv2.INTER_NEAREST` |
| `polygon[0]` 不是左上角 | zbar 不保证点序 | 用 OpenCV 的角点，或自己找最靠近 (min_x,min_y) 的点 |

## I. 自测题

**1. 为什么 `d = f × W / w` 里的 f 单位是像素，而不是镜头上印的焦距（比如 3.6mm）？**

<details><summary>答案</summary>
因为等式两边必须单位一致：`w(px)/f(px) = W(mm)/d(mm)`。
像素约掉、毫米约掉，两边都变成无量纲比值。如果 f 用 3.6mm，
左边就成了 px/mm，右边是 mm/mm，等式不成立。
物理上，"像素焦距" = 物理焦距 × 像素密度，它把"镜头的焦距"和"传感器的采样"合并成了一个你直接能测量的数。
</details>

**2. 投票为什么要求"严格过半"而不是"最多票"？举一个具体的翻车例子。**

<details><summary>答案</summary>
窗口里有 3 个结果各 1 票时，"最多票"会随便挑一个（取决于字典顺序），
等于把"我不确定"硬说成"我确定"。
具体例子：`['156+123+516+231', '156+123+5l6+231', '999+999+999+999']` 各 1 票，
最多票规则会输出 `156+123+5l6+231`（含非法字符 l）—— 一个**必然解析失败**的答案，
而且它还会覆盖掉之前已经稳定的正确答案。
</details>

**3. 为什么打印二维码时"逐格画矩形"比"画小再放大"好？**

<details><summary>答案</summary>
因为放大时插值会把相邻的黑白格平均成灰色的过渡带。
二维码的格必须是纯黑/纯白，灰边会让 zbar 的行列采样在两格之间摇摆，甚至判错格数。
逐格画矩形则是**从几何上保证每个格是纯色**（每次 `round()` 定位边界，不会有半格灰边）。
实测佐证：补白边 2x 双线性 → 读不出；补白边 2x 最近邻 → 读得出。
</details>

**4. 你在 2000mm 处读到码，码宽 60px。按 A 节表，这正常吗？该做什么？**

<details><summary>答案</summary>
`d = f×W/w = 1475×80/60 = 1967mm`，与 2000mm 基本吻合（误差 1.7%），说明你的 f 标定得很好。
但 60px = 2.07px/格，第 09 课同档命中率只有 75%，**能读到是运气**。
正确动作：**再往前挪 100~200mm**（目标 ≥80px / 2.76px/格），然后重新读并重新测距，形成闭环。
</details>

**5. D 节能救 `03_size_40.png` 吗？为什么？**

<details><summary>答案</summary>
**不能**（实测返回"OpenCV 没检测到码"）。
因为 `03_size_40.png` 整张图只有 40×40 像素、码占 1.38px/格，
OpenCV 的定位角检测同样需要每格足够像素才能找到三个定位图案。
D 节救的是"**看得见但读不出**"（透视、旋转），救不了"**根本找不到**"（太小、太糊、被挡）。
</details>

**6. 如果你的摄像头换成 1280×720，A 节的 f 还能直接用吗？**

<details><summary>答案</summary>
**不能**。换成 1280×720 后，同一个物体会成像在更多像素上，
`w` 变成 640×480 时的 2 倍，但相机**根本没换**（物理焦距没变）。
所以 f（像素焦距）= 物理焦距 × 像素密度，像素密度翻倍 → f 翻倍（约 2950px）。
**必须用新分辨率重新标定一次**。这也是 md 里强调"标定 3 次取平均"的原因：
你在不同分辨率、不同裁剪下都要确认 f。
</details>

## J. 小结

| 工具 | 核心公式 / 要点 | 关键坑 |
|------|---------------|--------|
| A 测距 | `d = f × W / w`，f 单位是像素，要标定 | 用最长边；只在标定距离 ±50% 内用 |
| B 投票 | `n * 2 > len(buf)` 严格过半；`None` 不占票 | 别用 `most_common(1)` |
| C 打印 | 300DPI → 1mm=11.811px；29 格 × 2.759mm = 80.0mm | 逐格画，别 resize；红线画在码外 |
| D 摆正 | OpenCV 给四角 + straight；每格 ≥2px + 最近邻 | 救"看得见读不出"，救不了"找不到" |
| E 条形码 | `r.type` 判型；QR 与一维码可共存 | `quality` 不可比（QR=1，EAN13=355） |

## K. 结课：你现在手里有什么

十二课下来，你不只是"会用 zbar 了"。你手里有：

1. **一套能跑的代码**：11 个脚本，每个都能独立运行、每个都有实测输出
2. **一套实测数字**：不是"大概能读"，而是"80px 时 100%、60px 时 75%、40px 时 0%"
3. **一套方法论**：控制变量、负样本、相位陷阱、按成本排序、把规则写成断言
4. **一套赛场工具**：能测距、能投票、能打码板、能给底盘对准、能读条形码

**但最重要的收获是那几个"翻案"**：

| 我教给你的（错的） | 实测告诉你的（对的） |
|-----------------|------------------|
| 白边（border）决定能不能读 | 单独白底 border=0 也能读；旁边有深色物才崩 |
| 放大必须用最近邻 | 好坏随采样方式互换，所以两种都放进流水线 |
| 60px 的码读不出 | 那是实验设计缺陷（亚像素相位没随机化）造成的假象 |
| 注释说"按成本从低到高排序" | 代码把最贵的三级排在第三位 —— 只有 profile 能抓出来 |
| straight 必须补白边再放大 8 倍 | 真正的要求是每格 ≥2px + 最近邻，白边只是保险 |

> **这张表才是这门课真正的核心。**
> 你以后会读很多教程、很多博客，它们里面**一定有类似的错的断言**。
> 你现在有了工具，可以**自己验**。
>
> **别背结论，学方法。** 十二课里所有的数字，你都可以用自己的摄像头重新测一遍——
> 而且**必须重测**，因为你的镜头、你的分辨率、你的光源，和我的都不一样。
