## 1. 为什么要做压测？

第 07 课的体检表告诉你"**能治 / 治不了**"。但它有个致命缺陷：**每种病只有一张图**。

一张图 = 一次实验。一次实验只能回答"这一次行不行"，回答不了"**有多大把握**"。

> **打个比方**：掷一次骰子出 6，你能说"这个骰子总是出 6"吗？不能。
> **至少掷 8 次、16 次，才敢说概率。**
>
> 第 07 课是"看病例"，第 09 课是"做统计"。**统计才能做决策。**

### 为什么不直接拿真摄像头拍 200 张？

因为**不可控**。你想单独测"码变小的影响"，但真实拍摄里码一变远，光照、角度、模糊全都跟着变。
**变量混在一起，结论就没法归因。**

所以我们**合成**画面：一次只改一个参数，其他全部锁死。
这叫**控制变量法**，是实验科学的基本功。

```python
# 一次只改一个参数，其余给默认值，结论才能归因
def make_scene(side, angle=0.0, blur=0.0, noise=0.0, brightness=1.0,
               jpeg=None, rng=None, bg=160, W=640, H=480):   # 后几个是场景固定值
    """合成一张"摄像头拍到的画面"：灰色背景 + 随机位置贴一个码 + 施加各种劣化。"""
```

> **⚠️ 合成实验的边界（必须承认）**
> 合成画面**永远不等于**真实画面。真实世界还有：镜头畸变、色差、卷帘快门、
> 反光、灰尘、贴纸褶皱……**压测的价值在于"找出关键因素"，不在于"预测真实命中率"。**
> **真正的最终验证，只能用真摄像头在真场地上做。**

## 3. 怎么读这张表：三列的含义完全不同

| 列 | 含义 | 你该拿它做什么 |
|----|------|---------------|
| **zbar** | 裸解码（第 03 课的做法） | 你的**基线**。它的天花板就是这个 |
| **zbar+预处理** | 失败后再试 中值→OTSU→2x 放大 | **花极小的代价换来多少提升**，看这一列比 zbar 高多少 |
| **OpenCV** | `cv2.QRCodeDetector`（完全不同的实现） | **对照组**：证明"这不是 zbar 独有的短板" |

> **为什么一定要有"对照组"？**

>
> **没有对照组的实验结论，只能算"现象"，不能算"知识"。**

## 4. 六个实验，六条能给赛场用的结论

### 结论 1：码要占 ≥80px，对应的其实是"车要开多近"

| 码边长 | 每格像素（÷29） | zbar | 含义 |
|--------|----------------|------|------|
| 40px | 1.38 | **0%** | 完全不行 |
| 60px | 2.07 | 75% | 看运气 |
| **80px** | **2.76** | **100%** | **稳定可用** |
| 100px | 3.45 | 100% | 稳 |
| 160px | 5.52 | 100% | 非常稳（OpenCV 也开始 100%） |

**"80px" 这个像素数很抽象。换成距离才有用。**

用第 12 课进阶 A 的公式（`d = f × W / w`），假设你的摄像头标定出 **f = 1475px**（焦距，单位像素），
二维码实际边长 **W = 80mm**：

| 码在画面里 | 车到码板的距离 | 能不能读 |
|-----------|--------------|---------|
| 200px | 590 mm | ✅ 稳 |
| 160px | 738 mm | ✅ 稳 |
| 120px | 983 mm | ✅ 稳 |
| 80px | **1475 mm** | ✅ 稳（临界） |
| 60px | 1967 mm | ⚠️ 75% |
| 40px | 2950 mm | ❌ 0% |

> **翻译成人话：用 f=1475px 的镜头，你必须在 1.5 米以内正对二维码板。**
> 场地是 2400×2400mm，二维码板贴在场地内侧 —— **1.5 米的余量其实很紧张**。
>
> **这就给了你三个可选决策**：
> 1. **换短焦镜头**（f 变小 → 同样 80px 对应更近的距离？不，是同样距离下码更大）→ 首选
> 2. **提高分辨率**（640×480 → 1280×720，同样视场下 80px 变 160px）→ 第二选择
> 3. **设计"必须靠近才能扫"的动作路径**（先走到板子前 1 米，读完再走）→ 最保险

> **怎么得到你自己的 f？** 拿码放在已知距离 `d0`，量出画面里码的像素宽 `w0`，则 `f = w0 × d0 / 80mm`。
> 例：码放 500mm 处、量得 236px → f = 236 × 500 / 80 = **1475px**。
> **这一步必须在你的车上实测，不能抄别人的数字。**

### 结论 2：歪 45° 都还行，但这是 zbar 的"隐藏优点"

zbar 在 0~45° 全都 100%，OpenCV 在 45° 只有 25%。

**为什么 zbar 这么抗旋转？** 因为二维码有三个定位图案（回字），zbar 用它们算出仿射变换，
**能直接从任意角度的四点采样**。而 OpenCV 的实现对极端角度的鲁棒性差一些。

> **赛场含义**：如果二维码板装在场地边缘、你的车只能斜着看，**zbar 是个好选择**。
> **但**：本实验只测了"平面内旋转"，没测"透视倾斜"（比如仰视 30°）。
> **透视才是真问题** —— 第 07 课的 `11_perspective.png` 就是透视，读得出但很勉强。
> **不要把这个 100% 当成"可以随便歪着拍"。**

### 结论 3：模糊 sigma ≥3 完全无解 —— 这是"必须停车"的硬证据

| 模糊 sigma | zbar | 含义 |
|-----------|------|------|
| 0~1 | 100% | 清晰 |
| 2 | 100%（OpenCV 掉到 38%） | 轻微模糊，zbar 还能扛 |
| **3 以上** | **0%（任何预处理都救不了）** | **彻底废** |

> **为什么预处理救不了模糊？**
> 模糊是把**信息"摊开"了**：一个黑格子的边界被平均成"黑→灰→灰→白"的渐变。
> 中值滤波、二值化、放大 —— 都只能在这片渐变上做文章，
> **但"这个格子到底是黑还是白"这个信息，已经在模糊那一步被摊平了。**
> 这和第 07 课的"反光斑"是同一类：**信息丢失，软件无解。**

**赛场含义（这条特别重要）**：

> **你的机器人必须在读码前"停下来"或"减速到几乎静止"。**
>
> 为什么？因为运动模糊的本质是"曝光期间画面在动"。
> 假设曝光时间 1/60 秒、车速 0.5 m/s，画面会拖出 **8.3mm 的位移**；
> 在 1.5 米外、80px 的码上，8.3mm 相当于 **约 11px 的拖影** —— 远超 sigma 3。
>
> **三个解法**：① 停车读码（最省事）② 缩短曝光时间（要更亮的光）
> ③ 用全局快门相机（卷帘快门会有"斜切"畸变）

### 结论 4：噪声 0.15 是 zbar 的分水岭，但"药方"能 100% 救回来

| 噪声 | zbar | +预处理 |
|------|------|---------|
| 0~0.1 | 100% | 100% |
| **0.15** | **0%** | **100%** ← 救回来了 |
| 0.2 | 0% | 100% |

**这是整份报告里最划算的一笔**：花 0.3ms（中值+OTSU），把 0% 变 100%。

> **但注意 zbar 耗时那一列在噪声档明显变高**（14ms → 25ms）。
> 因为噪点多 → zbar 看到很多"像码的东西" → 反复找 → **更慢**。
> **噪声既降低命中率，又拖慢速度 —— 双重损失。**

### 结论 5：亮度 0.2 都能读 —— 但别高兴太早

亮度从 1.0 降到 0.2（暗 5 倍），zbar 仍然 **100%**。为什么？

因为 zbar 内部做的是**局部自适应二值化**：它不看"绝对亮度"，只看"**对比度**"。
只要黑格子和白底还有落差，它就能切开。

> **⚠️ 但这个实验有个"作弊"之处**：`make_scene` 里的亮度是**统一乘一个系数**，
> 相当于"整体变暗"，**对比度保持比例不变**。
>
> 真实世界的"暗"往往伴随**噪声占比上升**（信噪比变差）和**动态范围压缩**。
> **所以别拿这一行当"光线不重要"的证据** —— 它只证明"zbar 不怕整体偏暗"。

### 结论 6：JPEG 质量 15 也 100% —— 压缩不是问题

JPEG 质量从 95 降到 15，全 100%（而且越快越省时间）。

**为什么？** 因为 JPEG 的方块状伪影主要出现在**高频细节**（平滑区域边缘），
而二维码是**大面积纯黑/纯白块**，压缩后仍然是黑和白。

> **赛场含义**：如果你的图传/录制用了 JPEG 压缩，**不用为此担心**。
> 时间预算也不用为"解压"留很多 —— 表中 JPEG 越低耗时反而越低（数据量小）。

## 5. 一个"方法论"大发现：亚像素相位

这是本课最有价值的部分，也是我写脚本时**真的踩到并修正**的一个实验设计错误。

### 5.1 起初的诡异现象

第一版脚本里，码边长这一列出现了**完全不符合直觉**的结果：

```
40px → 0%    50px → 100%    60px → 0%    70px → 100%
```

**50px 能读、60px 读不出、70px 又能读？** 尺寸越大反而更差？这不可能。

### 5.2 追查：8 次实验其实是"同一件事做了 8 遍"

问题出在这行代码：

```python
# ══════ 环境准备（每个示例都一样，照抄，不用改任何东西）══════
import os, sys
ROOT = "/home/kata/Desktop/logisticsCV/zbar二维码从零到赛场"   # 教程根目录
os.chdir(ROOT)                                    # 让示例里的 "assets/xxx" 找得到
sys.path.insert(0, os.path.join(ROOT, "code"))    # 让 import zbar_bootstrap 找得到
import zbar_bootstrap
zbar_bootstrap.ensure()                           # 确认 zbar 已就绪（第 02 课验证过）
from PIL import Image
from pyzbar.pyzbar import decode
# ══════════════════════════════════════════════════════════

# ═══ 1. 先造一个标准码当素材 ═══
import numpy as np, cv2                    # numpy 管像素数组，cv2 管缩放
import qrcode                              # 用库自己造码，代替实拍

rng = np.random.default_rng(2027)          # 固定种子：每次跑结果一样
W, H = 640, 480                            # 画面尺寸：常见 USB 摄像头分辨率
side = 60                                   # 码宽 60 像素（约 2.07 px/格）

qr = qrcode.QRCode(box_size=4, border=4)   # 每格 4px，四周留 4 格空白
qr.add_data("156+123+516+231")             # 塞进第 08 课那个任务码
qr.make(fit=True)                          # 按数据量自动挑最小版本

# 画成图再转 numpy 数组：fill 黑、back 白，L 表示灰度
qr_img = np.array(qr.make_image(fill_color="black", back_color="white").convert("L"))
# 缩到 side×side；缩小专用 INTER_AREA，边缘才有灰度过渡
qr_img = cv2.resize(qr_img, (side, side), interpolation=cv2.INTER_AREA)

# ═══ 2. 贴到灰底上：位置只取整数像素（问题就在这里） ═══
frame = np.full((H, W), 160, np.uint8)                        # 灰色背景
max_x, max_y = W - side, H - side                            # 贴图不许越界
x = int(rng.integers(0, max_x))     # 贴图位置：整数像素
y = int(rng.integers(0, max_y))                              # 纵向同样只取整数
frame[y:y + side, x:x + side] = qr_img                       # 把码盖到这块区域
print("贴到了整数像素位置：", (x, y))                          # 相位每次都一模一样
print("能不能读出来：", "OK" if decode(Image.fromarray(frame)) else "X")  # 8 次结果整齐
```

**位置是整数像素** —— 这意味着无论随机到哪，**格子边界与像素网格的相对位置永远一样**。
真正决定"这一档能不能读"的是**那个相对位置（亚像素相位）**，而它在这 8 次里**从未变过**。

所以 8 次结果不是概率，是**同一件事重复了 8 遍**（所以才 0/8 或 8/8 那么整齐）。

> **这是一个非常经典的实验设计错误：你以为你在测概率，其实你在测一个确定性的事实。**
> **识别它的信号是"结果太整齐"** —— 8/8 和 0/8 同时出现，说明有变量没控制住。

### 5.3 修正：加入亚像素相位抖动

```python
# ══════ 环境准备（每个示例都一样，照抄，不用改任何东西）══════
import os, sys
ROOT = "/home/kata/Desktop/logisticsCV/zbar二维码从零到赛场"   # 教程根目录
os.chdir(ROOT)                                    # 让示例里的 "assets/xxx" 找得到
sys.path.insert(0, os.path.join(ROOT, "code"))    # 让 import zbar_bootstrap 找得到
import zbar_bootstrap
zbar_bootstrap.ensure()                           # 确认 zbar 已就绪（第 02 课验证过）
from PIL import Image
from pyzbar.pyzbar import decode
# ══════════════════════════════════════════════════════════

# ═══ 修正：让每次摆放的位置都不一样 ═══
import numpy as np, cv2                    # numpy 管像素，cv2 管平移

# ★ 随机亚像素偏移（0~1 像素的任意小数）
rng = np.random.default_rng(2027)          # 种子照旧，结果仍可复现
W, H = 640, 480                            # 画面尺寸不变
frame = np.full((H, W), 160, np.uint8)      # 假设这就是粘好码的画面
dx, dy = rng.uniform(0, 1), rng.uniform(0, 1)   # 两个方向各取一个 0~1 小数
# 平移矩阵只改最后一列：格子跟着动，相位就变了
frame = cv2.warpAffine(frame, np.float32([[1, 0, dx], [0, 1, dy]]), (W, H),
                       flags=cv2.INTER_LINEAR, borderMode=cv2.BORDER_REPLICATE)   # 边缘复制防黑边
# 打印平移量核对：8 次各不相同，才算 8 个独立样本
print(f"整体平移了 ({dx:.3f}, {dy:.3f}) 像素 —— 这一步让 8 次实验真正是 8 个不同样本")
```

**为什么要这么做？** 因为真实摄像头每次采样时，**码在传感器上的位置都是亚像素级随机的**
（车在动、手在抖、机械误差）。**你的实验必须复现这种随机性，统计才有意义。**

### 5.4 修正后：结论变得清晰且惊人

```
【补充实验 2】亚像素相位：同一个『距离』，为什么有时读得出有时读不出？

  码边长         每格px   相位 0.0 → 0.9 的命中情况
  --------------------------------------------------------------
  56          1.93   ###..#####   = 8/10
  60          2.07   .####.####   = 8/10
  64          2.21   #####.####   = 9/10
  68          2.34   ##########   = 10/10
  80          2.76   ##########   = 10/10
```

**同一张码、同一个大小，只把图平移不到 1 个像素**，命中情况就变成一串 "####..####"。

> **这张表是全书最实用的一张表**。它的含义是：
>
> **在"每格 2 像素"附近，命中率不是 0 也不是 100，而是"看运气"。**
> 而"运气"= **码的格子边界恰好落在传感器的哪里**。
>
> **赛场上的直接后果**：车停在某个距离可能刚好读不出，**往前挪半厘米就读出了**。
> 学生会以为是"代码有 bug"，其实是**相位**问题。

**所以工程上的两条铁律**：

1. **不要贴着临界尺寸设计** —— 留 1.5 倍余量（要 80px 就按 120px 设计）
2. **失败了就"挪一点再读"** —— 平移 1~2 个像素对应的物理位移，往往就能救回来

> **第 10 课的 `RobustReader` 就是按这个思路设计的**：它不是"一帧定生死"，
> 而是"连续多帧 + 多种预处理 + 必要时换解码器"，
> **用"多试几次"来吃掉这种相位运气。**

## 6. 补充实验：插值选择（顺便推翻第 07 课的一句口诀）

第 07 课脚本最后打印过一句"放大要用最近邻，别用三次样条"。
**这里我们用数据检验它。**

两个场景分开测，因为**它们的像素来源不同**：

- **场景A 平滑缩小（INTER_AREA）**：像真实摄像头远距离拍摄，边缘有灰度过渡
- **场景B 硬边缩小（INTER_NEAREST）**：像打印机印的"1 像素 1 格"，边缘一刀切

<details>
<summary>参考结果（补充实验）</summary>

```
  ── 场景A 平滑缩小 ──
  码边长           不放大       最近邻       双线性      三次样条
  --------------------------------------------------
  28             0%        0%        0%        0%
  32             0%        0%        0%        0%
  36             0%        0%        0%        0%
  40             0%        0%        0%       19%
  44            19%        0%        0%       62%
  48            19%       12%       31%      100%

  ── 场景B 硬边缩小 ──
  码边长           不放大       最近邻       双线性      三次样条
  --------------------------------------------------
  28            19%       38%       12%       38%
  32             0%        0%        0%        0%
  36             0%       38%        0%        6%
  40             0%       44%        0%       19%
  44            44%       31%       31%       50%
  48            38%       38%       44%       56%

  数据说了什么？（下面每句都是从上面的表里算出来的）
    场景A 平滑缩小：不放大最好只有 19%，放大后最好 100%（用三次样条）
      各插值的最高分：最近邻 12%，双线性 31%，三次样条 100%
    场景B 硬边缩小：不放大最好只有 44%，放大后最好 56%（用三次样条）
      各插值的最高分：最近邻 44%，双线性 44%，三次样条 56%
```

</details>

### 读出来的三件事

**① "放大必须用最近邻"是错的。**
场景A 里最近邻最高只有 **12%**，三次样条 **100%** —— 差 88 个百分点。
同一档尺寸（48px），换个插值就从"基本读不出"变成"次次读出"。

**② 但也没有"永远正确的插值"。**
场景B 里三种插值都在 44~56% 徘徊，谁也没到 100%。
**说明真正决定成败的是"原图还剩多少信息"，插值只是在这个基础上尽力而为。**

**③ 所以正确做法是"都试一遍"。**
2x 放大 + 4x 放大 + 2~3 种插值 = 5~6 种组合，
每种成本 <0.1ms，**总成本不到 1ms**，换来"哪种图都能读"。

> **这就是第 10 课 `PIPELINE` 里同时有 L6(2x最近邻)、L7(4x最近邻)、L8(4x三次) 的原因。**
> **不是冗余，是"用 0.2 毫秒买保险"。**
>
> **这也是"算法组"和"调参组"的区别**：
> 调参组背口诀；算法组**测出口诀的适用边界，然后把边界写成代码**。

### 练习 9-A：算出你的"稳定距离"

用本课的公式，假设 f=1475px、W=80mm。要达到"稳定 100%"需要多少距离？
如果场地长 3 米、板子在对面墙上，你能不能从容读到？

```
d = f × W / w = 1475 × 80 / 80 = 1475 mm ≈ 1.48 m
```

**结论：稳定读码要求车离板 ≤1.48 米。**

场地 2400×2400mm（对角线 3.4m）。如果码板在对面墙，从对角最远处是 3.4m → **读不到**。
所以**必须设计"靠近再读"的路径**，或者换镜头/换分辨率。

> **这就是压测的价值**：它把一个"感觉能行"变成了"必须 ≤1.48m"这个硬约束，
> 而这个约束会直接改变你的路径规划代码。

### 练习 9-B：找出模糊的精确临界

超过 sigma=2 就掉到 0%。测 sigma=2.2、2.5，看它是不是"突然崩"还是"渐变崩"。

<details>
<summary>参考答案</summary>

```python
# ══════ 环境准备（每个示例都一样，照抄，不用改任何东西）══════
import os, sys
ROOT = "/home/kata/Desktop/logisticsCV/zbar二维码从零到赛场"   # 教程根目录
os.chdir(ROOT)                                    # 让示例里的 "assets/xxx" 找得到
sys.path.insert(0, os.path.join(ROOT, "code"))    # 让 import zbar_bootstrap 找得到
import zbar_bootstrap
zbar_bootstrap.ensure()                           # 确认 zbar 已就绪（第 02 课验证过）
from PIL import Image
from pyzbar.pyzbar import decode
# ══════════════════════════════════════════════════════════

# ═══ 1. 复用压测脚本里的零件 ═══
import sys, os                             # 只为拼路径
sys.path.insert(0, "code")                 # 让下面两个 import 找得到
import zbar_bootstrap; zbar_bootstrap.ensure()   # 先确保 zbar 能用
import numpy as np                         # 随机数发生器要用
import lesson09_stress as L9               # 复用造图/解码函数，不重写

# ═══ 2. 一个函数同时测"裸 zbar"和"加预处理" ═══
def rate(trials=16, **kw):                 # trials 次随机摆放，**kw 传劣化参数
    rng = np.random.default_rng(L9.SEED)   # 同一条随机流，各档才可比
    z = r = 0                              # z 记裸 zbar，r 记预处理后
    for _ in range(trials):                # 每次换一个随机摆放位置
        f = L9.make_scene(rng=rng, bg=160, **kw)   # 造一张该档条件的画面
        g = L9.test_zbar(f)                # 先按基线读一次
        z += g                             # True 当 1 加，省掉判断
        r += 1 if g else L9.test_zbar(f, rescue=True)   # 失败才上预处理
    return z/trials*100, r/trials*100      # 命中数 ÷ 次数 = 百分比

# ═══ 3. 在 2 到 3 之间细扫，看是断崖还是渐变 ═══
for sg in (2.0, 2.2, 2.5, 3.0):            # 码统一 160px，只动模糊
    a, b = rate(side=160, blur=sg)         # 两列命中率一起拿
    print(f"sigma {sg}  zbar {a:.0f}%  +预处理 {b:.0f}%")   # 0 位小数，够看
```

参考结果（本机实测）：

```
sigma 2.0  zbar 100%  +预处理 100%
sigma 2.2  zbar 100%  +预处理 100%
sigma 2.5  zbar 0%  +预处理 0%
sigma 3.0  zbar 0%  +预处理 0%
```

**结论：在 sigma 2.2 ~ 2.5 之间"突然崩"，不是渐变。**

> **这个"断崖"非常重要**：它意味着**没有"稍微模糊"这回事**。
> 你要么在安全区（sigma <2.2），要么在死亡区。
> **所以"读码前减速到静止"不是优化，是必需** —— 因为越界就是 0%，不是 90%。

</details>

### 练习 9-C：噪声药方的天花板

噪声 0.3、0.5 时，"中值+OTSU+2x"这套药方还能救吗？上限在哪？

<details>
<summary>参考答案</summary>

> **🚫 片段（不能单独运行）** —— rate 是压测脚本里的『命中率』统计函数，单独复制会报 `NameError: name 'rate' is not defined`。完整可运行版：`python code/lesson09_stress.py`。

```python
# 只改噪声：码保持 160px，逐档加噪看药方在哪失效
for ns in (0.15, 0.2, 0.3, 0.5):
    a, b = rate(side=160, noise=ns)        # 每档各测 16 次
    print(f"噪声 {ns}  zbar {a:.0f}%  +预处理 {b:.0f}%")   # 两列差就是药方的功劳
```

参考结果（本机实测）：

```
噪声 0.15  zbar 0%  +预处理 100%
噪声 0.2   zbar 0%  +预处理 100%
噪声 0.3   zbar 0%  +预处理 94%
噪声 0.5   zbar 0%  +预处理 0%
```

**药方的天花板在噪声 0.2 ~ 0.3 之间**（0.3 时掉到 94%，0.5 时彻底失效）。

> **为什么 0.5 就救不了了？** 因为噪声标准差 = 255×0.5 = 127，**超过黑白色差的一半**。
> 换句话说"黑白对比"已经被噪声淹没了 —— 中值滤波也分不清哪个是信号。
> **这是"信息丢失"，不是"信息脏"** —— 和模糊、反光、遮挡是同一类边界。

</details>

### 练习 9-D：相位平移的"物理换算"

在 1475mm 距离、80px 的码上，**1 个像素**对应多少毫米？
"平移 1 像素就能救回来"这件事，在物理上是"挪多远"？

<details>
<summary>参考答案</summary>

```
1 像素对应的物理宽度 = W / w = 80mm / 80px = 1.0 mm/px
```

**所以"平移 1 个像素"在物理上就是"挪 1 毫米"。**

> **这个换算极其有用**：它告诉你**相位问题的物理尺度是毫米级**。
> 车往前挪 1~2mm 就可能从"读不出"变成"读得出"。
>
> **对机器人的启示**：如果读码失败，**最简单的补救是"往前挪 2mm 再读"**，
> 而不是去改算法。**这个动作的代价几乎为零，成功率增益却很大。**
> （第 10 课的 `confirm` 机制本质上就是"多帧多个位置各试一次"。）

</details>

## 8. 常见错误

| 现象 | 原因 | 解法 |
|------|------|------|
| 实验结果是整齐的 0/8 或 8/8 | 某个变量没随机化（如整数像素位置） | 引入亚像素抖动 |
| 8 次实验只跑 3 秒，结论却写得很肯定 | 样本太少 | 至少 16 次；临界档至少 32 次 |
| 不同参数的结果互相矛盾 | 随机种子没固定 / 各档用了不同随机流 | 固定 `SEED`，同一档用同一条流 |
| OpenCV 那列时好时坏 | `QRCodeDetector` 有内部状态 | 每次 new 一个实例，或接受它的不稳定 |
| 测出来的命中率比真实高很多 | 合成图太干净 | 加 JPEG、加噪声、加相位抖动 |

## 9. 自测题

1. 为什么压测要用"合成画面"而不是直接拍 200 张真实照片？

   <details>
   <summary>参考答案</summary>

   真实拍摄里多个变量同时变化，无法归因；合成能一次只改一个参数（控制变量法）。代价是合成图不等于真实图，只能找关键因素，不能预测真实命中率。

   </details>

2. "zbar 一列 100%、OpenCV 一列 25%"这个对比，告诉你什么？

   <details>
   <summary>参考答案</summary>

   OpenCV 对旋转（尤其 45°）明显更弱，说明"抗旋转"不是任务本身的难度，而是 zbar 这个实现的强项；也说明换实现可能带来 4 倍差异，选型很重要。

   </details>

3. 为什么模糊超过 sigma 3 以后，任何预处理都救不了？

   <details>
   <summary>参考答案</summary>

   模糊把黑白边界摊成渐变，格子"到底黑还是白"的信息被抹平；中值/二值化/放大都只是在这片渐变上做文章，无法恢复已丢失的信息。

   </details>

4. "8 次实验全是 0/8"，这为什么是实验设计有问题的信号？

   <details>
   <summary>参考答案</summary>

   8 次独立实验全部相同，说明这 8 次没有独立变化，某个应随机的量（这里是亚像素相位）被固定了，所以测的不是概率而是确定性事实。

   </details>

5. 亚像素相位是什么意思？它对赛场有什么实际影响？

   <details>
   <summary>参考答案</summary>

   指码的格子边界相对于像素网格的亚像素级偏移。它使同一尺寸下的成败呈"看运气"状态，赛场上表现为"离得差不多但有时读不出"，对策是留余量、挪几毫米重读、多帧确认。

   </details>

6. 亮度降到 0.2 还能 100%，为什么不能因此认为"光线不重要"？

   <details>
   <summary>参考答案</summary>

   因为实验里的"变暗"是整体系数缩放，对比度比例保持不变，而 zbar 靠局部自适应二值化只看对比度。真实低光会同时降低信噪比、压缩动态范围，结论不能外推。

   </details>

## 10. 小结

| 你学到的 | 一句话 |
|---------|--------|
| 压测的意义 | 从"能不能"升级到"多大把握"，才能做决策 |
| 控制变量 | 合成场景一次只改一个参数，结论才可归因 |
| **尺寸阈值** | 640×480 下码 ≥80px（2.76px/格）才稳；换成距离 ≈1.48m（f=1475px） |
| **相位发现** | 每格 ~2px 时成败看亚像素相位；≥3px/格 才稳定 |
| 模糊 | sigma ≥2.5 **断崖式**归零，必须停车/缩短曝光 |
| 噪声 | 0.15 是分水岭，中值+OTSU 能 100% 救回（成本 0.3ms） |
| 亮度/JPEG | 整体变暗、JPEG 压缩都不是问题（别过度设计） |
| 旋转 | zbar 0~45° 全 100%，OpenCV 45° 只有 25% |
| 时间预算 | 找不到码时 13~15ms（扫全图），按最坏情况留 |
| 插值 | "必须用最近邻"被推翻；正确做法是多种插值都放进流水线 |
| 实验纪律 | 结果太整齐 = 有变量没随机化；样本要够 |
