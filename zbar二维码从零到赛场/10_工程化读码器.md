## 1. 脚本和模块差在哪？

先看你现在手里的东西。第 03 课的写法是：

```python
results = decode(cv2.cvtColor(cv2.imread(path), cv2.COLOR_BGR2GRAY))
print(results[0].data.decode() if results else "没读到")
```

这段代码在**你自己电脑上**完全正确。但如果把它塞进机器人的主循环，会立刻暴露三个缺口：

| 缺口 | 具体会怎么翻车 | 赛场上长什么样 |
|------|--------------|--------------|
| **① 没确认** | 单帧读到就算数 | 反光/屏摄偶发读串一个字符，机器人搬错颜色 → 0 分 |
| **② 没兜底** | 只跑一次原图 | 车停得偏一点、码小一点，就"读不出"，站在那里不动 |
| **③ 没预算** | 不知道最坏要多久 | 万一碰上噪声画面，一帧 540ms，主循环卡死 → 撞障碍物 |

> **打个比方**：脚本是**实验室里的电路原型**，插着杜邦线、露着铜丝，能用，但你不能把它装进产品。
> 模块化就是**把原型焊到板子上、装进壳子里、留好散热孔**。
> 功能一个没变，但从"能跑"变成"敢用"。

这一课就是把这三个缺口补上。补法不是加 if-else 补丁，而是**重新组织代码结构**。

## 2. 设计：三层抽象

整个读码器只有三层，非常薄：

```
① 级别（level）      一个函数，输入图 → 输出"喂给 zbar 的图"
        ↓  用列表串起来
② 流水线（PIPELINE）  [(名字, 级别), ...]  按成本从低到高排
        ↓  被一个对象持有
③ 读码器（RobustReader） read(frame) → (任务码 或 None, 哪一级救的)
```

**为什么要拆成三级，而不是写一个大函数？**

因为这三层的变化频率完全不同：

- **级别**经常增删（今天加个锐化，明天发现没用删掉）→ 独立小函数，改一个不影响别的
- **流水线顺序**偶尔调（实测后发现放大太贵，挪到最后）→ 只是一个列表，改顺序不用改代码
- **读码器**几乎不动（确认逻辑、预算逻辑是稳定的）→ 一旦写好就复用

> **这是软件工程里最常见的分层理由**：把"经常变的"和"很少变的"分开。
> 反过来做——把所有处理硬写进一个大函数——你今天改一行，明天就不知道会碰坏哪里。

### 2.1 一个级别长什么样

现在看真代码（`code/lesson10_reader.py:47-104`）。级别函数有严格契约：**吃一张图，吐一张图**。

```python
def _gray(img):
    """统一入口：BGR 三通道和灰度单通道都收。"""
    return img if img.ndim == 2 else cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)


def lv_raw(img):
    """L0 原图灰度。成本 ≈ 0.01ms（只是可能有一次颜色转换）。"""
    return _gray(img)


def lv_median(img):
    """L1 中值滤波 3x3。治椒盐噪声。成本 ≈ 0.02ms。"""
    return cv2.medianBlur(_gray(img), 3)


def lv_otsu(img):
    """L2 OTSU 二值化。治低对比度/光照不均。成本 ≈ 0.05ms。"""
    g = _gray(img)
    return cv2.threshold(g, 0, 255, cv2.THRESH_BINARY + cv2.THRESH_OTSU)[1]
```

**注意 `_gray()` 这个设计**：每个级别都先调它。

为什么要多这一层？因为读码器的输入可能来自：
- `cv2.imread()` → BGR 三通道
- `cap.read()` → BGR 三通道
- 别人给你的灰度图 → 单通道
- `cv2.QRCodeDetector` 返回的 straight → 单通道

如果每个级别都自己写 `if img.ndim == 3: cvtColor(...)`，就是 **9 份重复代码**，
哪天要支持 BGRA 四通道，你得改 9 个地方。

> **一句话原则**：**重复三次以上的代码，就该抽成一个函数。**
> 抽出来的东西有个名字（`_gray`），别人才看得懂你在干什么。

## 3. 流水线为什么这么排？（一次真实的自我纠错）

这是全课最重要的一节。因为**我第一版排错了**。

### 3.1 第一版（错的）

```python
PIPELINE = [
    ("L0 原图", lv_raw),
    ("L1 中值", lv_median),
    ("L2 OTSU", lv_otsu),
    ("L3 放大2x", lv_up2),        # ← 问题在这
    ("L4 放大4x", lv_up4),        # ← 和这
    ("L5 三次4x", lv_up4_cubic),  # ← 和这
    ("L6 CLAHE", lv_clahe),
    ("L7 反色", lv_invert),
    ("L8 中心裁剪", lv_center_crop),
]
```

而文件里那行注释写的是：

```python
# 顺序就是"从便宜到贵"，这是因为越贵的预处理越慢，
# 而 90% 的正常帧在 L0 就成功了 —— 那 90% 的帧不该为小概率的坏帧付钱。
```

**注释说得非常对。代码完全没照做。** 三级放大排在 L3~L5，而它们恰恰是最贵的三级。

> **这就是"注释是谎话"的经典案例**：写代码的时候脑子里想的是理论（放大不就是个 resize 吗，能多贵），
> 手就顺手把"放大"排在"滤镜"旁边了。**只有真去 profile（测耗时）一次，谎话才会露出来。**

### 3.2 实测剖析（640×480 画面，每级含 zbar 解码）

| 级别 | 纯灰空图（无码） | 灰底 + 高斯噪声 σ=20 |
|------|---------------:|-------------------:|
| L0 原图 | 2.0 ms | 25.4 ms |
| L1 中值 | 1.9 ms | 16.2 ms |
| L2 OTSU | 2.4 ms | 26.2 ms |
| **放大2x** | **9.2 ms** | **59.8 ms** |
| **放大4x** | **26.3 ms** | **146.8 ms** |
| **三次4x** | **26.0 ms** | **161.3 ms** |
| CLAHE | 2.2 ms | 27.3 ms |
| 反色 | 2.0 ms | 26.1 ms |
| 中心裁剪 | 1.5 ms | 15.0 ms |
| **合计** | **73.5 ms** | **504.1 ms** |

**三级放大占了 61.5ms / 73.5ms（干净画面）和 367.9ms / 504.1ms（噪声画面）。**

为什么放大这么贵？算一笔账就懂了：

```
640×480 的图，放大 4 倍边长 → 2560×1920
像素数从 307200 变成 4915200 —— 整整 16 倍
zbar 要在 16 倍的像素里找定位角、跑扫描线 → 时间大致也 ×16
```

> **而放大只治一种病：码太小。**
> 第 09 课实测：80px 以上的码，L0 原图 100% 能读。
> 换句话说 **95% 的帧根本不需要放大**，可第一版却让它们先付 61ms 的过路费。

### 3.3 修正后的顺序

```python
PIPELINE = [
    ("L0 原图", lv_raw),            # ≈2ms  90% 的帧在这就走了
    ("L1 中值", lv_median),         # ≈2ms  椒盐噪声唯一解药
    ("L2 OTSU", lv_otsu),           # ≈2ms  低对比度
    ("L3 CLAHE", lv_clahe),         # ≈2ms  发灰/偏暗
    ("L4 反色", lv_invert),         # ≈2ms  罕见的浅码深底
    ("L5 中心裁剪", lv_center_crop), # ≈2ms  码在正中但偏小
    ("L6 放大2x", lv_up2),          # ≈9ms  ← 从这里开始贵
    ("L7 放大4x", lv_up4),          # ≈26ms
    ("L8 三次4x", lv_up4_cubic),    # ≈26ms
]
```

排序依据三条，**按优先级**：

1. **成功率高且便宜的排前面**（L0~L2，解决 90%+ 的帧）
2. **成功率低但也很便宜的紧随其后**（L3~L5，反色只治罕见病，但它只要 2ms，试一下不亏）
3. **又贵又只治单一病的排最后**（L6~L8，放大）

> **反色为什么不能排第一？** 因为它不只"没用"，是**有害**的：
> 正常码（黑码白底）反色后变成白码黑底，zbar 的默认配置读不出来。
> 第 07 课实测：`01_clean.png` 反色后直接读不出。
> 所以它必须排在"通用药都试过之后"，但它又便宜，所以排在"昂贵药之前"。
>
> **这个位置是算出来的，不是拍脑袋定的**：便宜（2ms）+ 专用（低概率）→ 夹在中间。

## 4. 读码器本体逐行精读

### 4.1 状态机的三个属性

```python
def __init__(self, confirm=2, use_opencv_fallback=True, verbose=False,
             budget_ms=None):
    self.confirm = max(1, confirm)          # 要连续几次一致
    self.use_opencv_fallback = use_opencv_fallback
    self.verbose = verbose
    self.budget_ms = budget_ms              # 单帧时间上限
    self.stats = Counter()                  # 每级成功次数
    self.frames = 0                         # 处理了多少帧
    self.confirmed = None                   # 最终确认的任务码
    self._streak = Counter()                # 连续命中计数
    self.skipped = 0                        # 因超预算被放弃的帧数
```

`self._streak` 是**核心状态**，它的类型是 `Counter`（计数字典），
含义是"**当前连续读到某个内容多少次**"。

为什么不用一个简单变量 `self.last_text` + `self.count`？

因为 Counter 有个好处：**不同内容的计数天然隔离**。
假设第 5 帧读到 A、第 6 帧读到 B、第 7 帧又读到 A——

- 用 `last_text` 方案：第 6 帧一变，A 的计数就被清零，第 7 帧的 A 要从 1 重新数
- 用 Counter 方案：A 的计数**还留着**，但**永远不会被 `read()` 采信**，因为要求的是"连续"

等等，那 Counter 不是白存了吗？**没白存，它是给 `verbose` 调试看的**。
真正决定"连不连续"的是 `read()` 里那句 `self._streak.clear()`：

```python
def read(self, frame):
    self.frames += 1
    text, level = self._read_raw(frame)
    if text is None:
        self._streak.clear()      # ← 一旦读不到，全部清零（这是"连续"的定义）
        return None, None

    self._streak[text] += 1
    if self._streak[text] >= self.confirm:
        self.confirmed = text
        return text, level
    return None, level
```

**这三行就是"连续 N 次"的全部实现**：读不到 → 清零；读到了 → 对应内容 +1；攒够 → 采信。

> **⚠️ 一个容易被忽略的语义选择**：`text is None` 就清零，意味着
> **中间夹一帧读不到，连续就断了**。
>
> 这是"严格连续"。还有一种是"宽容的连续"（比如 5 帧里读到 3 次就算），
> 那种叫**滑动窗口投票**，第 12 课 B 节会实现。这里我们先用最严格的，
> 因为它**不引入额外延迟**，而且对"读串码"免疫。

### 4.2 流水线循环 + 预算检查

```python
def _read_raw(self, frame):
    t0 = time.perf_counter()
    for name, fn in PIPELINE:
        if (self.budget_ms is not None
                and (time.perf_counter() - t0) * 1000 > self.budget_ms):
            self.skipped += 1          # 超预算：这一帧放弃，别拖住主循环
            return None, None
        try:
            r = decode(fn(frame))
        except Exception as e:          # 预处理本身不该炸掉主循环
            if self.verbose:
                print(f"    {name} 预处理异常：{e}")
            continue
        if r:
            self.stats[name] += 1
            return r[0].data.decode("utf-8", "replace"), name
```

三处细节值得停下来看：

**① `t0` 记在循环外，检查在每一级之前。**
这意味着预算检查的粒度是"一级"，最坏会超出一级的耗时（约 26ms）。
想更精细就得在级别函数内部查——那不值得，**因为 26ms 的误差换来的是一行干净的代码**。

**② `except Exception` 兜的是"预处理炸了"，不是"没读到"。**
这两件事必须分开：

| 情况 | 处理方式 | 理由 |
|------|---------|------|
| 中值滤波抛异常（图太小/格式怪） | `continue` 去下一级 | 这一级瘸了，别让整帧废掉 |
| zbar 返回空列表（没找到码） | `if r:` 自然跳过 | 这是**正常的**，不是错误 |

> **第 03 课强调过**：没读到**不是异常**。如果给"没读到"也 try/except，
> 你的 except 会一秒执行 30 次，真错误就淹在里面看不见了。

**③ `r[0]` 只取第一个结果。**
因为我们是"找到一个就够"的场景（一块板子一个码）。
第 03 课练习 3-C 埋过伏笔：**返回顺序不保证**（实测发现右边先出）。
真要处理多码（比如同时读任务码 + 位置码），得遍历并**按 `rect.left` 排序**，
不能用 `r[0]`。

## 5. 时间预算：为什么必须允许"主动放弃"

### 5.1 实测三档（640×480）

| 画面 | 每帧耗时 | 等效帧率 | 说明 |
|------|--------:|--------:|------|
| **有码，L0 就成功**（`13_scene.png`） | **3.0 ms** | 333 fps | 最好的情况 |
| **无码，纯灰空画面** | 82.2 ms | 12.2 fps | 11 级全跑完才放弃 |
| **无码 + 噪声 σ=20** | 540.1 ms | 1.9 fps | 最坏情况 |
| **无码 + 噪声 + 轻微模糊** | 171.0 ms | 5.8 fps | 模糊让 zbar 更早放弃 |

**有码 3ms，没码 82~540ms —— 差 27 到 180 倍。**

为什么没码反而更慢？因为 zbar 找到码就能提前收工，
而**没找到码时它要把整张图的所有扫描线走一遍**，
噪声画面里还有一堆"像码的假目标"要逐个排除。

> **这是反直觉的工程事实**：读码器最贵的时候，恰恰是"什么都没读到"的时候。
> 而机器人大部分时间都在"没读到码"的状态里（在路上跑）。
> 如果你不设预算，你的主循环帧率会被一块**没码的灰墙**拖到 1.9fps。

### 5.2 预算怎么设

```bash
# 不设预算（默认）：跑完 11 级，最坏 540ms
.venv/bin/python code/lesson10_reader.py --image assets/_blank_no_qr.png

# 设 40ms：跑到 40ms 就放弃这一帧
.venv/bin/python code/lesson10_reader.py --image assets/_blank_no_qr.png --budget 40
```

实测对比：

```
不设预算：耗时 78.9 ms / 实际处理 1 帧（平均 78.9 ms 每帧）

--budget 40：耗时 42.5 ms / 实际处理 1 帧（平均 42.5 ms 每帧）
             ⚠ 有 1 帧因为超出 40.0ms 预算被主动放弃。
```

**推荐值 30~50ms**，理由：

- 摄像头出图本身约 45ms（第 06 课实测，占端到端 85%）→ 主循环本来就只有 20fps 左右
- 读码占 40ms 时，端到端约 85ms ≈ 12fps，**对"停车后对着板子读"完全够用**
- 真正的读码时刻（车停了、板子在视野正中），L0 通常 3ms 就成功，根本不会触发预算

> **思路**：预算是给"坏帧"准备的安全带，不是给"好帧"用的。
> 好帧 3ms，安全带永远不勒到它。

### 5.3 预算的行为边界（实测）

```bash
# 01_clean.png 设 budget=0.5（比 L0 还快，理论上啥都跑不完）
.venv/bin/python code/lesson10_reader.py --image assets/01_clean.png --budget 0.5
```

结果：

```
命中帧数        : 1（100.0%）
耗时：1.9 ms / 实际处理 1 帧（平均 1.9 ms 每帧）
```

**还是读到了。** 为什么？因为检查在每级**之前**：

```
进入循环 → 检查(0ms > 0.5ms? 否) → 跑 L0 → 命中 → return
```

**L0 永远有机会跑。** 这是有意设计的：**第一级是"什么都不做"，它绝不该被预算砍掉**，
否则你这个读码器就变成了"永远返回 None"的废件。

## 6. 三种输入源，一种调用方式

```python
def source_from_args(args):
    if args.image:      # 单张图片 → [img]
    if args.replay:     # 回放 60 帧 → [img, img, ...]
    cap = cv2.VideoCapture(args.camera)   # 摄像头 → 抓 N 帧
    ...
    return frames, name
```

**关键设计：都返回 `list[ndarray]`。** 单张图片就是一个长度为 1 的列表。

为什么要统一成列表？因为这样 `read()` 的使用者（主循环）**不需要区分来源**：

```python
frames, name = source_from_args(args)
for f in frames:
    text, level = reader.read(f)
```

对比一下不统一的写法会多出什么：

```python
# 如果不统一，你得到处写这种分叉
if args.image:
    text, level = reader.read(img)
else:
    while True:
        ok, f = cap.read()
        if not ok: break
        text, level = reader.read(f)
```

**一次统一，处处简单**。这是接口设计里最划算的买卖。

> **真实工程提示**：摄像头抓帧我们用的是"先抓 60 帧存进内存再处理"，
> 而不是"边抓边处理"。因为**离线帧率测量**要求处理和采集解耦——
> 否则摄像头等 45ms、处理等 3ms，两者混在一起，你根本分不清慢在哪一步。
> 上车时当然要改成边抓边处理（第 06 课 md 里有完整循环）。

**这张表里最容易被忽略的是最后两行**：`09_occluded` 和 `08_glare` 是**故意要失败的**。

```python
cases = [("01_clean.png", True), ("06_noise.png", True),
         ("03_size_30.png", True), ("09_occluded.png", False),
         ("08_glare.png", False)]
```

第二列 `should_pass` 表示"**预期能不能读到**"。这叫**负样本**（negative sample）。

> **为什么必须要有负样本？**
> 假设你改坏了代码，让 `decode()` 永远返回一个固定的假答案，
> 那么 3 个正样本全过 —— 测试"通过"了，但你的读码器是个废物。
> **只有负样本能揭穿它**：09_occluded 应该读不出，如果它读出了，说明检测逻辑有严重bug。

> **这就是为什么第 8 课 md 里我写**："如果哪天它们突然能读了，反而要怀疑是不是读错了（假阳性）。"

### 练习 10-A　给每一级记账

写一个脚本，对 `01_clean.png`、`13_scene.png`、`03_size_30.png` 三张图，

<details>
<summary>参考答案</summary>

```python
import os, sys, time
sys.path.insert(0, "code")
import cv2
import lesson10_reader as R


def timeit(fn, img, n=5):
    s = time.perf_counter()
    for _ in range(n):
        fn(img)
    return (time.perf_counter() - s) * 1000 / n


for name in ("01_clean.png", "13_scene.png", "03_size_30.png"):
    img = cv2.imread(os.path.join(R.ASSETS, name))
    print(f"  {name}:")

    for lname, fn in R.PIPELINE:
        t = timeit(lambda im: R.decode(fn(im)), img)
        tot += t
        print(f"    {lname:<12}{t:7.2f} ms")
    print(f"    {'合计':<12}{tot:7.2f} ms")
```

**实测结果**：

| confirm | 第几帧确认 | 命中帧数 | 处理帧数 | 耗时 |
|--------:|----------:|--------:|--------:|-----:|
| 1 | **第 6 帧** | 1（16.7%） | 6 | 537.1 ms |
| 2 | **第 9 帧** | 3（33.3%） | 9 | 798.8 ms |
| 3 | **第 10 帧** | 4（40.0%） | 10 | 902.0 ms |

**怎么读这张表**：

- `confirm=1`：第 6 帧第一次读到就认账，**最快**（6 帧 / 537ms）
- `confirm=2`：等到第 9 帧（第 8、9 帧连着都读到），**多花 3 帧 ≈ 262ms**
- `confirm=3`：等到第 10 帧，**再多花 1 帧**

每帧都能读到。**这 3 帧不是"确认机制的固定成本"，而是"画面刚好在那时候才连续清晰"。**

> **决策**：取 `confirm=2`。
> 理由：多付出 1 帧（在读得到之后）就能免疫单帧误读；
> 而 confirm=3 只多挡一类极罕见情况（连续两帧读到同一个错答案），不划算。
> **赛场上"晚 33ms 确认"完全不影响成绩，但"搬错一个颜色"直接 0 分。**

</details>

### 练习 10-C　预算砍在哪儿

<details>
<summary>参考答案</summary>

```bash

```

**实测结果**：

```
  这一段没读到能确认的码。
  命中帧数        : 0（0.0%）
  耗时：6.0 ms / 实际处理 1 帧（平均 6.0 ms 每帧）
  ⚠ 有 1 帧因为超出 3.0ms 预算被主动放弃。
```

**为什么失败**：`06_noise.png` 要靠 **L1 中值** 才能读到。
而 L1 之前的 L0 在噪声图上要跑满一次完整扫描（噪声里全是假目标），
第 09 课实测噪声画面单级就要 16~26ms —— **3ms 连 L0 都没跑完，根本轮不到 L1。**

**这揭示了一个真实的权衡**：

| 预算 | 好帧（有码） | 坏帧（噪声无码） |
|------|-------------|----------------|
| 不设 | 3ms 成功 | 540ms |
| 40ms | 3ms 成功 | 40ms 放弃 |
| **3ms** | 3ms 成功 | **6ms 放弃 —— 但连救回来的机会都没了** |

> **结论**：预算设得太紧，等于**放弃了"努力一下能读到"的那部分帧**。
> 40ms 是"努力一次"的成本上限；3ms 是"根本不努力"。
> **赛场上车是停着读的，有的是时间，所以 40ms 甚至 100ms 都行；行驶中才需要紧预算。**

</details>

### 练习 10-E　给读码器加一条"最稳"的退出条件

现在的退出条件是"连续 confirm 次读到同一内容"。**再给一个安全阀**：
"处理满 N 帧还读不到，就放弃整段，别死循环"。
写一个 `read_until(source, reader, max_frames)` 循环，带帧数上限。

<details>
<summary>参考答案</summary>

```python
def read_until(source, reader, max_frames=120, verbose=True):
    """从输入源里读，直到确认或帧数耗尽。返回 (任务码 或 None, 用掉几帧)。"""
    for i, frame in enumerate(source):
        if i >= max_frames:
            break
        text, level = reader.read(frame)
        if verbose and (i + 1) % 20 == 0:
            print(f"    ...已处理 {i + 1} 帧，确认状态：{reader.confirmed}")
        if text:
            return text, i + 1
    return None, min(len(source), max_frames)
```

**用法**（配合第 06 课的摄像头循环）：

```python
frames, name = source_from_args(args)
text, used = read_until(frames, reader, max_frames=len(frames))
if text is None:
    print("整段都没读到 → 该做的动作：倒车 5cm 再读（而不是原地死等）")
```

**为什么要有 `max_frames`**：因为 **`for f in frames` 本身就会终止**，
但真实摄像头是**无限流**——你写 `for f in cap` 会永远跑下去。
第 06 课 md 里我踩过这个坑（真摄像头不带 `--frames` 就是死循环）。
**任何"读源"的循环都必须有上限**，这是硬规矩。

</details>

## 9. 常见错误

| 现象 | 原因 | 修法 |
|------|------|------|
| 读码器 100% 返回 None | `budget_ms` 设成 0 或极小 | 检查预算；L0 之前就 return 了的话说明设成了负数 |
| 每帧都跑 500ms | 没设预算 + 画面有噪声 | `--budget 40` |
| 一直读到但从不确认 | `confirm` 设太大，或画面在抖 | 降到 2；或改用第 12 课滑动窗口投票 |
| `stats` 里 L0 从不为 0，但别的级也常常命中 | 正常，说明画面质量在漂移 | 不用管 |
| `--survey` 说有 4 张失败就以为坏了 | 其中 2 张**本来就没有码** | 看第 7.3 节的原因表，别对着没码的图调参 |
| `--camera` 卡死不出结果 | 没给 `--frames`，摄像头无限流 | 一定给帧数上限 |

## 10. 自测题

**1. 为什么 `_read_raw` 里的 `except Exception` 只包住 `decode(fn(frame))`，而不是包住整个循环？**

<details><summary>答案</summary>
因为要区分"某一级出问题"和"整个流程出问题"。包住单个 `decode` 调用，意味着某一级抛异常时
只 `continue` 到下一级，其他级别照跑；如果包住整个循环，任何一级炸了都会让整帧直接失败，
**丢掉本可以被后面级别救回来的帧**。更重要的是：范围越小，异常越容易定位。
</details>

**2. 为什么"有码 3ms、没码 82ms"？这个反直觉现象的物理原因是什么？**

<details><summary>答案</summary>
zbar 的流程是"先找定位角，再解码"。找到码就能**提前收工**；
找不到就必须把整张图的**所有行、所有列扫描线走完**才敢断言"没有码"。
所以"成功"是短路路径，"失败"是穷尽路径。噪声画面更糟：噪声会产生大量"像码的假目标"，
zbar 要逐个尝试解码（每个都要跑纠错），于是耗时暴涨到 540ms。
</details>

**3. 预算检查为什么放在"每一级之前"而不是"每一级之后"？**

<details><summary>答案</summary>
放之前 = 保证"不会开始一个肯定超时的级别"，但允许当前级别跑完（最多超出一级，约 26ms）。
放之后 = 会先跑完一个已经超时的级别再退出，语义上没区别但代码多一行。
更关键的是**放在之后会让 L0 也被检查一次**——如果 L0 花 1.2ms 而预算 0.5ms，
放之后就会"跑完 L0、读到、然后因为超时把结果丢掉"，这是荒谬的。
</details>

**4. 为什么 `--survey` 里 `21_display_panel.png` 失败**说明**读码器没问题**？

<details><summary>答案</summary>
因为那张图是"任务码显示面板的示意图"（第 08 课生成的黑底亮绿字面板），
**上面根本没有二维码**。读码器对没有码的图返回"读不出"是正确行为。
把它算进"失败"只是因为它在那 33 张资产里，不代表能力不足。
**判断失败原因比统计失败数量更重要。**
</details>

**5. `confirm=2` 和"第 12 课的滑动窗口投票"有什么本质区别？**

<details><summary>答案</summary>
- `confirm` 要求**严格连续**：中间夹 1 帧读不到，连续就断了，从头数
- 滑动窗口投票看的是"**最近 N 帧里某个内容出现了几次**"，允许中间有断点

严格连续**不引入额外延迟**但更脆（画面一抖就重新数）；
投票更宽容但需要缓冲 N 帧（N=5 时引入最多 5 帧延迟）。
**停车读码用严格连续（快），行驶中扫读用投票（稳）。**
</details>

**6. 如果老板要求"读码必须 60fps"，你怎么回答？**

<details><summary>答案</summary>
先问"60fps 是指什么"，因为这句话有三种解读，成本差 20 倍：
1. **端到端 60fps**（含采集）→ 不可能。摄像头出图本身 45ms（第 06 课实测），物理上限 22fps。
2. **处理 60fps**（只算读码）→ 好帧 3ms 可以（333fps），坏帧 82~540ms 不行。
   → 答：**设 15ms 预算，好帧 60fps，坏帧降级放弃**。
3. **"平均"60fps** → 可以，但要在"没码的帧"降低扫描频率（比如每 3 帧才全流程扫一次）。

**这是工程沟通的基本功**：把一句模糊需求拆成可测量的三种口径，然后给出各自的成本。
</details>

## 11. 小结

| 你学到的 | 一句话 |
|---------|--------|
| 脚本 vs 模块 | 模块要有：确认、兜底、预算、统计 |
| 三层抽象 | 级别（函数）→ 流水线（列表）→ 读码器（对象） |
| **按成本排序** | 实测：三级放大占 61.5/73.5ms；它们必须排最后 |
| 注释 ≠ 代码 | 第一版注释写着"从便宜到贵"，代码却把放大排第三 —— profile 才抓出来 |
| 反色的位置 | 便宜（2ms）+ 专用病 → 夹在"通用药之后、昂贵药之前"（L4） |
| 连续确认 | `_streak.clear()` 一行就是"连续 N 次"的完整实现 |
| **时间预算** | 有码 3ms、无码 82ms（带噪 540ms）；上车必须设 30~50ms |
| 预算语义 | 检查在每级**之前** → L0 永远有机会跑，超时最多一级 |
| 负样本 | 自检必须包含"应该失败"的用例，否则改坏了也测不出来 |
| 统计口径 | "平均 89ms/帧"可能只是"那段时间画面很差"，别拿去当帧率上限 |
| 接入解析器 | 抓 `TaskCodeError` 当"这帧没读到"，继续读，不要崩 |

## 12. 下一课衔接

到这一课，**读码这件事已经完整闭环**：

- 读得出（第 03–06 课）→ 读得稳（第 07、09 课）→ 读得出"结构化意图"（第 08 课）→ **装成模块**（本课）

但还有一件没做的事：**把它放进整台车里**。

一块码读出来了，然后呢？
- 车怎么知道自己在哪？（定位）
- 怎么走到板子前面？（路径规划）
- 路上撞到障碍物怎么办？（避障）
- 读码和抓取抢同一个 CPU 怎么办？（资源调度）

第 11 课不再写新代码，而是**把前面 10 课的所有知识点串成一张图**，
让你看清"读码"在整个搬运任务里到底站在哪个位置、和谁交接、交付什么格式的数据。
