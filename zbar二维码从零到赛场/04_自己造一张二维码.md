## 1. 本课要解决的问题

赛场上有个很讨厌的事实：

> **你手上没有码。** 任务码是裁判现场抽签生成的，你连题目都看不到。

所以你必须会**造**码，理由有三：

| 理由 | 说明 |
|------|------|
| **造考题** | 自己造出 `156+123+516+231`，才能提前练"读到之后怎么解析、怎么搬运" |
| **做压测** | 想知道"码多小会读不出"，就得能造出各种尺寸的码（第 09 课全靠这个） |
| **搞懂参数** | 造码时有 4 个参数必须填，**填错就读不出**。这是理解 QR 结构最快的方式 |

> **批注：这一课是"从消费者变成生产者"。**
> 只会 `decode()` 你是**用别人做的码**；会造码你就能**自己设计实验**。
> 后面每一课的实验图，其实都是这个库造出来的（见 `code/make_assets.py`）。

### 最小造码代码

```python
# ══════ 环境准备（每个示例都一样，照抄，不用改任何东西）══════
import os, sys
ROOT = "/home/kata/Desktop/logisticsCV/zbar二维码从零到赛场"   # 教程根目录
os.chdir(ROOT)                                    # 让示例里的 "assets/xxx" 找得到
sys.path.insert(0, os.path.join(ROOT, "code"))    # 让 import zbar_bootstrap 找得到
import zbar_bootstrap
zbar_bootstrap.ensure()                           # 确认 zbar 已就绪（第 02 课验证过）
from PIL import Image
from pyzbar.pyzbar import decode
# ══════════════════════════════════════════════════════════

import qrcode

qr = qrcode.QRCode(
    version=None,                                  # None = 让库自己按内容选
    error_correction=qrcode.constants.ERROR_CORRECT_M,   # 纠错等级
    box_size=10,                                   # 每个小方格放大成多少像素
    border=4,                                      # 四周留几格白边
)
qr.add_data("156+123+516+231")                     # 塞内容
qr.make(fit=True)                                  # 排布格子
img = qr.make_image(fill_color="black", back_color="white").convert("RGB")
img.save("assets/generated/my_first_qr.png")
```

```

第 1 步：造出第一张码，并读懂它的『体检报告』
==================================================================
内容        : 156+123+516+231（15 个字符）
版本 version: 1   ← 版本 1 = 21x21 格；每升一版每边 +4 格
有效格数    : 21 x 21 = 441 个方块
纠错等级    : 0  (1=L 0=M 3=Q 2=H)
白边 border : 4 格

验算        : (有效格 21 + 白边 8) x 每格 10px = 290px  ← 与图片尺寸一致
读回来验证  : 156+123+516+231
```

### 这一份报告里有 4 个知识点

**① 版本号决定格子数**

```
version 1  → 21 × 21 格
version 2  → 25 × 25 格
version 3  → 29 × 29 格
...每升一版，每边 +4 格
```

为什么是 +4 而不是 +1？因为每升一版，码里要多装**一个对齐图案**（第 01 课提过的
右下角那个小方块），而一个对齐图案占 5×5 格，加上间隔正好推着边长走 4 格。
**这是标准设计者算好的**，你记住"每版 +4"就够用。

**② 图片尺寸的万能公式**

```
图片边长 = (有效格数 + 2 × border) × box_size
        = (21 + 2×4) × 10
        = 29 × 10
        = 290 px
```

> **这个公式请务必记住**，它是第 09 课算"码有多小"的基础。
> 反过来用更重要：**看到图片尺寸，就能反推每格几像素。**

**③ `纠错等级: 0` 这个数字是什么鬼？**

那是 `qrcode` 库内部的整数值（`ERROR_CORRECT_M` 的真实值是 0）。
它和 `L=1 / Q=3 / H=2` 的对应关系**非常反直觉**，所以脚本里把它自己标出来了。
**别背这个数字**，永远用常量名 `ERROR_CORRECT_M`。

**④ "读回来验证"这一行是自尊心**

造完码一定要 `decode()` 一遍。为什么？
因为**造码的参数组合非常多，很容易造出一张"看起来像二维码、其实读不出"的图**
（本课练习 4-E 就会造出这种图）。**造完就读，是肌肉记忆级别的习惯。**

## 3. 动手 2：四档纠错等级，代价是什么？

第 01 课说过纠错能让码"脏了还能读"。现在实测它的**代价**：

### 参考结果（第 2 步）

```
==================================================================
第 2 步：同样的内容，四档纠错等级，代价是什么？
==================================================================
等级    版本    有效格       图片边长      能救回多少
------------------------------------------------------------------
L     1     21        290       约 7%
M     1     21        290       约 15%
Q     1     21        290       约 25%
H     2     25        330       约 30%
------------------------------------------------------------------
看出来的规律：
  · L→Q 阶段版本没变（都是 version 1，21x21 格），因为内容够短，装得下。
  · 到 H，同样的字塞不进 21x21 了，库自动升到 version 2（25x25 格）。
  · 格数一多，同样印成 80mm 的话每格就更小 → 摄像头更难看清。
  → 这就是工程上的权衡：抗污损 ↑ 但可读距离 ↓。赛场建议 M 或 Q。
```

### 为什么 H 会突然升版本？

因为**纠错码本身也要占格子**。同样 21×21 的容量里：

```
L 级：数据格很多，纠错格很少  → 装得下
H 级：数据格只剩 1/2 左右，纠错格要 30% → 装不下，只好升到 25×25
```

> **打个比方**：一个箱子装东西。
> L 是"只垫一层泡沫"，能装很多东西但怕摔；
> H 是"垫三层泡沫"，安全但装不下原来那么多。
> **泡沫是要占地方的，不是白送的。**

> **批注：这里藏着一个"反常识"的实测结果。**
> 你可能以为"内容越长版本越高"。但注意 `156+123+516+231` 只有 15 个字符，
> 却因为全是 `0-9` 和 `+`，走了 QR 标准里最省空间的**字母数字模式**
> （这个字符集是 `0-9 A-Z $ % * + - . / :`，每 2 个字符只占 11 比特）。
> 所以哪怕 H 级也只需要 version 2。
>
> **实用推论**：赛题任务码永远是数字和 `+`，只占 15 个字符 → **版本只会是 1 或 2**。
> 这意味着你**永远知道码有多大**（21 或 25 格），可以提前算好摄像头要多近才能看清。
> **这是赛题给你的一个隐藏礼物**，很多人没注意到。

### 赛场怎么选？

| 等级 | 抗污损 | 格子密度 | 建议 |
|------|-------|---------|------|
| L | 7% | 最低 | 打印环境完美、距离远时用 |
| **M** | 15% | 低 | **默认推荐**，容错和距离平衡 |
| **Q** | 25% | 低 | 赛场有反光/污损时推荐 |
| H | 30% | 高一档 | 代价是格子更密，反而更难读清 |

**结论：H 不是"最好"，是"最贵"。** 反光严重的场合用 H 有时反而更容易失败 ——
因为它把每格做得更小了。

## 4. 动手 3：只改"每格几像素"和"白边"，信息量会变吗？

### 参考结果（第 3 步）

```
==================================================================
第 3 步：只改『每格几像素』和『白边』，信息量会不会变？
==================================================================
box_size=2   图片   58x58   有效格还是 21x21  读回：156+123+516+231
box_size=4   图片  116x116  有效格还是 21x21  读回：156+123+516+231
box_size=10  图片  290x290  有效格还是 21x21  读回：156+123+516+231
box_size=20   图片  580x580  有效格还是 21x21  读回：156+123+516+231

border=0  图片 210px  单独白底读回：156+123+516+231
border=1  图片 230px  单独白底读回：156+123+516+231
border=2  图片 250px  单独白底读回：156+123+516+231
border=4  图片 290px  单独白底读回：156+123+516+231

但是——把码贴到板子上，旁边紧挨着深色块时，白边就变成生死线了：
border=0  左侧紧贴黑条  ：读不出来 ← 安静区被黑条吃掉了
border=2  左侧紧贴黑条  ：156+123+516+231
border=4  左侧紧贴黑条  ：156+123+516+231

结论：单独放在白底上时，border=0 也能读出来（zbar 很宽容）；
     但只要旁边有深色东西（板子边框、支架、阴影），白边不够就立刻崩。
     二维码标准规定 ≥4 格，就是为这种情况留的余量。
     你在排版打印时不要为了『省地方』把白边裁掉。
```

### 结论 1：`box_size` 只买"清晰度预算"，不买信息量

不管 `box_size` 是 2 还是 20，**有效格永远是 21×21，内容永远是那 15 个字符**。
它只改变"同一份信息被画成多少个像素"。

用第 01 课的语言说：**`box_size` 就是"每格几像素"那个旋钮。**

### 结论 2：白边（安静区）—— 一个被我实测纠正的传言

我原本准备这么写："白边是死线，border=0 一定读不出。"
**实测打脸了**：单独放在白底上时 `border=0` 照样读得出。

但真正致命的情况是**旁边有深色东西**：把码贴到板子上、左边紧挨一条黑边，
`border=0` 立刻崩，`border=2` 就活了。

> **为什么？回到第 01 课的原理：**
> zbar 找一个定位图案，要先确认"这是 1:1:3:1:1 的五段黑白交替"。
> 如果码外面紧贴着黑条，**那个"外圈的白"就没了** —— 五段变成四段，
> 定位图案认不出来。
> 单独放白底时，图片边界之外被当成了白色（或者 zbar 用别的方式兜住了），所以侥幸能读。

> **这条经验对赛场的意义**：
> 赛场上的二维码是贴在 **A4 白板**上的，板子本身有边框、有阴影、有支架。
> 如果你自己排版打印时为了"省地方"把白边裁到 1 格，**第一天可能没事，
> 换个光照角度就突然读不出** —— 而你在赛场上只有一次机会。
> **标准写"≥4 格"不是保守，是给意外留余量。**

> 为什么？因为远处的码可能属于别的赛场、或者是物料上的干扰标签，
> 而中心那个才是你的摄像头真正对准的。
> 第 05 课我们会用 `rect` 算出"码离画面中心多远"。

## 6. 动手 5：坑 —— 二维码里存中文

### 参考结果（第 5 步）

```
==================================================================
第 5 步：坑 —— 二维码里存中文，读回来为什么报错？
==================================================================
原始字节     : b'\xe6\x90\xac\xe8\xbf\x90\xe4\xbb\xbb\xe5\x8a\xa1\xef\xbc\x9a\xe7\xba\xa2\xe9\xbb\x91\xe6\xb5\x85\xe8\x93\x9d'
字节长度     : 27 （如果不按字节存，7 个汉字不可能塞进这么点）
按 UTF-8 解  : 搬运任务：红黑浅蓝

解释：二维码本身只存『一串字节』，不规定编码。qrcode 库默认按 UTF-8 写，
     所以读的时候也要用 UTF-8 解。赛场任务码是纯数字和加号，不会踩这个坑，
     但如果你以后要读中文标签，记得统一用 .decode('utf-8')。
```

**"搬运任务：红黑浅蓝" 是 9 个汉字（含冒号），为什么只占 27 字节？**

因为**一个 UTF-8 汉字 3 字节**，9 个字符 × 3 = 27 字节。这是 UTF-8 的设计：
英文字母 1 字节、汉字 3 字节。所以"见字知长"：**看到 27 字节就知道是 9 个汉字**。

> **批注：为什么 `.decode()` 会炸？**
> Python 的 `bytes.decode()` **默认用 UTF-8**。
> 如果码里存的是 GBK 中文（有些国产软件会这么干），你 `d.data.decode()` 就会抛
> `UnicodeDecodeError`。稳妥写法：
>
> ```python
> raw = d.data
> for enc in ("utf-8", "gbk", "latin-1"):     # 依次试，latin-1 永远不报错
>     try:
>         text = raw.decode(enc)
>         break
>     except UnicodeDecodeError:
>         continue
> ```
> 赛题任务码是纯 ASCII，用不上这个兜底。**但"备一个兜底"是竞赛代码的基本修养**。

## 7. 动手 6：造一张"赛场同款" 80×80mm 的码

命题文件里写得很明确：

> 二维码位于板中间，**尺寸 80×80mm**（含边框）。

问题是：**80mm 是物理尺寸，你的图片是像素。** 中间怎么换算？

```
需要的像素 = 80mm × DPI / 25.4
           = 80 × 150 / 25.4
           = 472 px      （150 DPI）
           = 945 px      （300 DPI）
```

### 参考结果（第 6 步）

```
==================================================================
第 6 步：造一张『赛场同款』80x80mm 的码（按 150 DPI 算）
==================================================================
80mm @150DPI = 472px 见方，实际存成 472x472
每格宽度     = 16.28px  ← 这是『能不能被看清』的物理下限
读回验证     : 156+123+516+231

提示：每格小于 2px 时，很多解码器就开始不稳。
     所以摄像头分辨率不是越高越好，而是要让『码在画面里够大』。

本课生成的文件都在：/home/kata/Desktop/logisticsCV/zbar二维码从零到赛场/assets/generated
```

**关键数字：80mm ÷ 29 格 = 2.76mm/格。**
（29 = 21 有效格 + 8 格白边）

> **这个 2.76mm 是本教程后面反复出现的"生死线"。**
> 第 09 课的压力测试会告诉你：**在 640×480 的摄像头画面里，这个码要占据多大，
> 才能稳定读出。** 先记住 2.76mm/格，到时候自己乘。

> **批注：为什么这里用 150 DPI，而第 12 课要 300 DPI？**
> 因为**用途不同**：
> - 150 DPI 是"屏幕上做实验"够用（472px 的码，zbar 读得动）
> - 300 DPI 是"真的拿去打印"（打印机需要更高分辨率，否则格子边缘会糊）
>
> 第 12 课的进阶 C 会用 300 DPI 生成一张**可以直接打印的 A4 板**
> （`assets/30_print_board_a4.png`，码正好 80.0mm），那时你会看到"逐格画"
> 和"缩放"的差别 —— 这是本教程最硬核的一张图。

> **200 个数字和 100 个字母居然是同一个版本？**
> 因为 `"8"*200` 全是数字，走的是最省的**纯数字模式**（每 3 个数字只占 10 比特），

> **模式不同，容量差一倍。** 这是 QR 标准里的三重优化（数字 / 字母数字 / 字节）。

**报错了。** 这句 `Data size (96) > size available (72)` 精确地告诉你：
需要 96 比特，但 version 1 的 H 级只给 72 比特。

> **这是本课最有价值的一课之一**：
> `fit=True` 的意思是"内容优先，装不下就升版"；
> `fit=False` 的意思是"版本优先，装不下就报错"。
> **默认的 `fit=True` 会偷偷改变你指定的参数** —— 这是很多"我以为我固定了版本"的 bug 来源。

**4-D**

```
version 1：21 有效格 + 8 格白边 = 29 格 → 80mm ÷ 29 = 2.759 mm/格
version 2：25 有效格 + 8 格白边 = 33 格 → 80mm ÷ 33 = 2.424 mm/格
```

**结论：version 1 每格更大（2.76mm > 2.42mm），更容易被摄像头看清。**
这就是第 3 节说的"H 级不一定更好"的定量证明：
**升级 = 格子变密 = 每格变小 = 可读距离变短。**

## 9. 常见错误

| 报错 / 现象 | 原因 | 解法 |
|------------|------|------|
| `DataOverflowError` | 内容装不下指定的 version（`fit=False`） | 用 `fit=True`，或换更高 version |
| 造出来的码读不出 | `border=0` 且周围有深色背景；或 `box_size` 太小 | `border=4`、`box_size≥4` |
| `version` 和你指定的一样，但内容被截断 | **不会发生**：qrcode 会报错而不是截断 | 说明你设了 `fit=False`，改用 `fit=True` |
| 中文读回变乱码 | `.decode()` 用了错误的编码 | 依次试 `utf-8` / `gbk` |
| 打印出来读不出 | DPI 太低导致格子糊在一起 | 用 300 DPI，且每格 ≥2mm |
| `img.save` 报 `KeyError: 'JPEG'` | `make_image()` 返回的是 `PilImage` 包装对象 | 先 `.convert("RGB")` 再 save |

## 10. 自测题

1. 图片边长、有效格数、`border`、`box_size` 之间的公式是什么？
2. 同样内容，为什么 `H` 级可能比 `M` 级**更难**被摄像头读到？
3. `border=0` 的码在什么情况下能读、什么情况下必崩？
4. `fit=True` 和 `fit=False` 的区别？哪个更容易悄悄改掉你指定的 `version`？
5. 任务码印成 80mm，`M` 级每格多少毫米？`H` 级呢？
6. 一张 21×21 像素的码读不出，为什么放大 10 倍就能读？

<details>
<summary>参考答案</summary>

1. `图片边长 = (有效格数 + 2×border) × box_size`；反向：`每格像素 = 边长 ÷ (有效格数 + 2×border)`。
2. H 级纠错码占格子多，同内容可能要升版本（21→25 格），印成同样 80mm 时每格从 2.76mm 缩到 2.42mm，更难看清；且每格采样误差更大。
3. 单独放在白底上能读（图片外侧被当成白色）；一旦码外侧紧贴深色物（黑条、边框、阴影），定位图案的"外圈白"被吃掉，必崩。
4. `fit=True` 内容优先、装不下自动升版本；`fit=False` 版本优先、装不下抛 `DataOverflowError`。**`fit=True` 会悄悄改掉你指定的 version。**
5. M 级：29 格 → 80/29 = **2.759 mm/格**；H 级：33 格 → 80/33 = **2.424 mm/格**。
6. 信息（格子黑白）一直都在，缺的只是"每格有足够像素让解码器采样"。放大用最近邻补回像素，格子边界依然是硬边，所以能读。

</details>

## 11. 小结

| 旋钮 | 改什么 | 不改什么 |
|------|--------|---------|
| `version` | 格子数（每版 +4 格/边） | —— |
| `ec` 纠错等级 | 抗污损 %／占格数 | 内容本身 |
| `box_size` | 每格几像素（清晰度预算） | **信息量、格子数** |
| `border` | 安静区宽度（≥4 格） | **信息量、格子数** |

三条要记住的：

1. **`fit=True` 会悄悄升版本** —— 想钉死版本必须 `fit=False` 并处理 `DataOverflowError`
2. **白边不是"锦上添花"，是"旁边有深色时的救命线"**
3. **任务码只占 15 个字母数字字符 → 版本只会是 1 或 2 → 格子数你永远知道**
