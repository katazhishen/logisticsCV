## 1. 本课要解决的问题

医生看病先量体温、测血压，再开药。
调程序也一样：**先确认"工具链"是好的，再去怀疑"我的代码写错了"。**

新手最常浪费时间的场景是这样的：

```python
from pyzbar.pyzbar import decode          # ← 报错 ImportError：缺的是 C 库
```

然后开始怀疑人生：是 pip 装错了？是不是要重装 Python？

其实八成只是**系统里缺一个 C 库**（`libzbar.so.0`）。
`pyzbar` 只是一个"翻译官"，它自己不会读码，它调用的是系统里的 zbar 本体。
翻译官在，但老板不在，当然干不了活。

所以这一课我们做两件事：

1. 写一个**体检脚本**，把"能不能跑"的每一环都检查一遍
2. 讲清 zbar 本体怎么装：**系统 apt 装**（本机现状）和**没有 sudo 时的绕法**（兜底方案）

> 这也解释了一个常见困惑：
> "我 `pip install pyzbar` 成功了，为什么还报错？"
> 因为 pip 只装了**翻译官**，老师傅（libzbar）是 apt 装的，pip 管不到。

```python
# fn 是"怎么检查"，hint 是修法提示
def check(name, fn, hint=""):
    """跑一项检查。fn 正常返回就给 [OK]，抛异常就给 [X]。"""
    global ok_count         # 计数在函数外，这里要能改它
    try:                    # 一项出错不该中断整场体检
        detail = fn()       # 真干活的一句：查什么由 fn 决定
        # 有细节就补在后面，没细节只打名字
        print(f"  [OK] {name}" + (f" —— {detail}" if detail else ""))
        ok_count += 1       # 通过了记一笔，末尾报总数
        return True         # 让调用方也知道这项过了
    except Exception as e:  # 兜住所有异常，体检不能断
        # 打异常类型和消息，方便照着搜
        print(f"  [ X] {name} —— {type(e).__name__}: {e}")
        if hint:            # 有修法才多打一行
            print(f"       修法：{hint}")   # 告诉读者怎么救
        bad.append(name)    # 记下名字，最后汇总失败清单
        return False        # 失败也正常返回，不再外抛
```

这是**整个脚本的灵魂**：把"检查"抽象成一个函数，传进去"怎么检查"（`fn`）。
这样加一项检查只需要一行 `check(...)`，不用复制粘贴一堆 `try/except`。
（这个套路叫**回调**，你在后面写读码流水线时会反复用到它 —— 第 10 课就是
"把一堆预处理函数塞进一个列表，一个个试"。）

## 4. 动手 2：理解"自检为什么这么写"

看 `code/env_check.py` 里检查摄像头的那一段：

```python
def _camera():
    import cv2                  # 只有这项要用 OpenCV，就地导入
    for i in range(4):          # 摄像头常注册成多个节点，只能试
        cap = cv2.VideoCapture(i)     # 试着打开第 i 号设备
        if cap.isOpened():            # 打不开就换下一个编号
            good, frame = cap.read()  # 能打开也可能没画面，再取一帧
            cap.release()             # 立刻松开设备，别一直占着
            if good and frame is not None:      # 取帧成功才算可用
                h, w = frame.shape[:2]          # 帧是(高,宽,通道)，别弄反
                # 把设备名和分辨率一起报出来
                return f"/dev/video{i} 可用，画面 {w}x{h}"
    raise RuntimeError("没找到可用摄像头")      # 4 个都试完才报错
```

**两个细节值得学**：

1. **为什么试 4 个编号？**
   本机 `/dev/video0`~`/dev/video3` 都存在，但实测只有 0 和 3 能出 640×480，
   1 和 2 是 360×360 而且 `ioctl` 直接报错。Linux 上一个摄像头常常注册成好几个
   设备节点（一个用于取流、几个用于元数据）。**不试一遍你不知道哪个能用。**

2. **为什么 `cap.read()` 之后还要判断 `frame is not None`？**
   `isOpened()` 只说明"打开了设备"，不保证"能取到画面"。
   这是**防御式编程**：宁可多写一行判断，不要在后面某个奇怪地方崩掉。

   你会发现整套代码里到处都是这种写法 —— 因为赛场上"莫名其妙崩一次"就是 0 分。

## 5. zbar 本体：两条路，一条正路一条兜底

**先说结论（本机现状）**：你已经 `sudo apt install libzbar0` 装好了系统版，
所以 `env_check.py` 报的是 `使用系统安装的 libzbar`，**本课这一节你只需要"读懂"，不需要"照做"**。

那为什么这一节还留着？两个原因：

1. **它是真实踩坑的记录**：这份教程最初就是在"没有 sudo"的前提下写出来的，
   里面踩的每一个坑（`LD_LIBRARY_PATH` 无效、pyzbar 只认一个名字）都是真的。
2. **你们要去的地方大概率又没有 sudo**：赛场的比赛机、队里公用的树莓派、
   Jetson、队友的笔记本 —— 你不可能每次都拿到 root。**备用路线必须会。**

两条路线对照：

| | 正路：`apt` 装系统库 | 兜底路：自带 `vendor/` + bootstrap |
|---|---|---|
| 需要 root | **需要** | **不需要** |
| 装的是什么 | `/lib/x86_64-linux-gnu/libzbar.so.0` | `vendor/lib/libzbar.so.0` |
| 怎么生效 | `ldconfig` 缓存里有了，`find_library('zbar')` 直接返回 | 手动 `CDLL` 预加载 + 猴补丁 `find_library` |
| 本机 `env_check` 报什么 | `使用系统安装的 libzbar` ✅（现状） | `使用教程自带的 vendor/lib/libzbar.so.0` |
| 适合场景 | 自己的开发机 | 赛场机、树莓派、借来的电脑 |

> **关键设计**：`code/zbar_bootstrap.py` 里第一句就是 `if find_library("zbar"): return "system"` ——
> **先走正路，走不通才兜底**。所以你装完系统库之后**一行代码都不用改**，
> 它会自动切到系统版。这就是**优雅降级 / graceful degradation**：
> 让"有条件的机器用好的，没条件的机器也能跑"。

下面 5.1~5.4 是这个兜底方案为什么必须这么写。

### 5.1 先看看到底缺什么

```bash
# pyzbar 是怎么找 zbar 的？答案在它自己的源码里
# （先确认 pyzbar 装在哪：python -c "import pyzbar, os; print(os.path.dirname(pyzbar.__file__))"）
grep -n "find_library" "$(python -c 'import pyzbar,os;print(os.path.dirname(pyzbar.__file__))')/zbar_library.py"
```

本机参考结果（conda 环境 `OpenCV_Linux` 下，行号与你看到的可能略有差别）：

```
60:    load_libzbar() 内部大致是这样：
61:        zbar = ctypes.util.find_library('zbar')
```


**这意味着**：pyzbar 只认 `ctypes.util.find_library('zbar')` 的返回值，
**别的名字一律不试**（比如 `libzbar.so.0`、绝对路径，它都不会自己去找）。

### 5.2 为什么设 `LD_LIBRARY_PATH` 也没用？

很多老教程会说"设个环境变量就行了"：

```bash
export LD_LIBRARY_PATH=/path/to/vendor/lib     # ← 实测无效
```

**为什么无效？** 因为 `ctypes.util.find_library()` 在 Linux 上不走
`LD_LIBRARY_PATH` 那套动态链接器的搜索逻辑。它干的事是：

1. 去问 `ldconfig -p`（系统级的库缓存）—— 我们没 sudo，装不进缓存
2. 退而求其次，试 `gcc -lzbar` 能不能链接 —— 同样找不到

> **打个比方**：`LD_LIBRARY_PATH` 是"在小区门口贴个新地址牌"，
> 但 `find_library` 是"打电话问物业要地址簿"。你贴的牌子它根本不看。

### 5.3 我们的解法：绕到它后面，直接把包裹塞到手上

`code/zbar_bootstrap.py` 全文只有 11 行：

```python
import ctypes, ctypes.util, os, sys         # ctypes 能直接调用 C 库
HERE = os.path.dirname(os.path.abspath(__file__))           # 本文件所在的 code/
LIB = os.path.join(os.path.dirname(HERE), "vendor", "lib")  # 退一层进 vendor/lib

# ensure()：缺库时才动手，返回它走了哪条路
def ensure():
    if ctypes.util.find_library("zbar"):        # 问到地址就不再往下走
        return "system"          # 系统里已经装好了，什么都不用做
    cand = os.path.join(LIB, "libzbar.so.0")    # 兜底的候选：自带的那个库
    if not os.path.exists(cand):
        raise RuntimeError("找不到 " + cand)    # 连自带库都没有，只能报错
    ctypes.CDLL(cand, mode=ctypes.RTLD_GLOBAL)  # 加载进内存，全局可见
    # 猴补丁：pyzbar 来问地址，就报这个路径
    ctypes.util.find_library = lambda name, *a: cand if name == "zbar" else None
    return "bundled"                            # 告诉调用方走的是自带库
```

**三句话看懂它**：

1. `if ctypes.util.find_library("zbar"): return "system"`
   → **先试正路**。你在有 sudo 的机器上 `apt install libzbar0`，这里就直接返回了，
   后面两行根本不会执行。**这就是"优雅降级"：不破坏正常环境。**
2. `ctypes.CDLL(cand, mode=ctypes.RTLD_GLOBAL)`
   → 手动把 `vendor/lib/libzbar.so.0` **加载进内存**。
   `RTLD_GLOBAL` 的意思是"把它放进全局符号表"，这样后面别人再找 zbar 的函数也能找到。
   （不加这个参数，加载完了别人还是看不见，等于白干。）
3. `ctypes.util.find_library = lambda ...`
   → **猴补丁（monkey patch）**：把 pyzbar 用来问地址的那个电话，改成我们的假电话 ——
   只要它问 `"zbar"`，就回答"在 `/…/vendor/lib/libzbar.so.0`"。
   因为 ②已经把它加载进内存了，pyzbar 拿到这个路径再 `CDLL` 一次只会得到同一个句柄，
   不会真的重复加载。

> **打个比方**：
> ② 是你先把快递送到收件人手上（库已经在内存里了）；
> ③ 是你顺手把物业的地址簿改了一行，让后面来问的人都得到这个地址。
> 两件事都得做：只做②，pyzbar 问地址还是问不到；只做③，路径指向的文件没被加载，
> `CDLL` 会真的去磁盘上找 —— 其实也能成，但**先加载**能保证"整个进程里只有一份 zbar"，
> 避免符号冲突。

### 5.4 zbar 本体是怎么来的？（两条路的具体命令）

**正路（你这次用的，需要 sudo）**：

```bash
sudo apt install -y libzbar0        # 只装库，pyzbar 就够用了
sudo apt install -y zbar-tools      # 可选：顺带装命令行工具 zbarimg
```

装完验证（这三条都该有输出）：

```bash
dpkg -l | grep libzbar                       # ii  libzbar0  0.23.92-4build2
ls -l /lib/x86_64-linux-gnu/libzbar.so.0     # → libzbar.so.0.3.0
python -c "import ctypes.util; print(ctypes.util.find_library('zbar'))"
# 输出：libzbar.so.0      ← 说明 pyzbar 那句 find_library 现在能问到了
```

> **注意**：`libzbar0` 和 `zbar-tools` 是两个包。
> `libzbar0` 是**库**（pyzbar 要的就是它），`zbar-tools` 是**命令行工具 `zbarimg`**。
> 本机目前装了前者、没装后者 —— 不影响教程（`vendor/zbarimg` 照样能用）。

**兜底路（没有 sudo 时，教程当初走的就是这条）**：

```bash
apt-get download libzbar0 zbar-tools      # 只下载，不安装（不需要 root）
dpkg -x libzbar0_*.deb  vendor/           # 解压到指定目录（不需要 root）
```

结果就是 `vendor/lib/libzbar.so.0` 和 `vendor/zbarimg` 都躺在那儿了。

> **`vendor/zbarimg` 是什么？**
> zbar 官方的**命令行工具**。调试时非常好用 —— 不写一行 Python 就能读码：
>
> ```bash
> ./vendor/zbarimg assets/01_clean.png
> ```
> 参考结果：`QR-Code:156+123+516+231`
>
> 这给你一个**排查思路**：
> - `zbarimg` 能读、Python 不能 → 问题在 Python 这一端（bootstrap / pyzbar）
> - `zbarimg` 也读不出 → 问题在图片本身（太小 / 太糊 / 没码）
>
> **"用一个更简单的工具交叉验证"**，是所有调试的基本功。

### 5.5 动手：在一台机器上把两条路都验一遍

你现在**两条路都有条件跑**（系统库已装 + `vendor/` 也在），所以可以亲手确认
"兜底代码不是摆设"。做法很简单：**假装系统里没有 zbar**。

本课已经把这段代码备好了，直接跑：

```bash
python code/probe_two_paths.py
```

它做的事就是下面这三步（**建议你照着敲一遍**，猴补丁这种技巧看十遍不如敲一遍）。
这段和 `code/probe_two_paths.py` 是同一件事，只是少了注释、更适合逐行读：

```python
# ══════ 环境准备（每个示例都一样，照抄，不用改任何东西）══════
import os, sys
ROOT = "/home/kata/Desktop/logisticsCV/zbar二维码从零到赛场"   # 教程根目录
os.chdir(ROOT)                                    # 让示例里的 "assets/xxx" 找得到
sys.path.insert(0, os.path.join(ROOT, "code"))    # 让 import zbar_bootstrap 找得到
import zbar_bootstrap
zbar_bootstrap.ensure()                           # 确认 zbar 已就绪（第 02 课验证过）
from PIL import Image
from pyzbar.pyzbar import decode
# ══════════════════════════════════════════════════════════

import ctypes.util                  # 要篡改的就是它里面的 find_library

# ① 正路：什么都不改，让 bootstrap 自己判断
print("默认情况 ensure() ->", zbar_bootstrap.ensure())      # 预期打出 system

# ② 兜底路：把 find_library 篡改成"永远找不到"，模拟没有 sudo 的机器
ctypes.util.find_library = lambda name, *a: None            # 换成永远说"没有"
print("强制兜底 ensure() ->", zbar_bootstrap.ensure())      # 预期打出 bundled

# ③ 两条路都能读码，才算真的验完
print("兜底路线读码 ->", decode(Image.open("assets/01_clean.png"))[0].data.decode())   # 读得出才算通
```

**本机实测输出**：

```
默认情况 ensure() -> system
强制兜底 ensure() -> bundled
兜底路线读码 -> 156+123+516+231
```

> **注意 ② 的技巧**：`ctypes.util.find_library = lambda name, *a: None` 是**猴补丁的猴补丁** ——
> 我们用它先把"正路"堵死，好让 `ensure()` 走进兜底分支。
> **这是测试"降级路径"的通用手法**：想验证备用逻辑，就把主逻辑人为弄坏。
> （第 09 课你会看到同一个思路：想验证"预处理有用"，就先造一个原图读不出的场景。）

> **为什么这个练习值得做？** 因为"兜底代码从来没被执行过"是最常见的隐性 bug。
> 你以后会在赛场机器上第一次执行它 —— 那时候才发现路径写错了，就太晚了。

## 6. 常见错误：报错信息 → 原因 → 解法

| 报错 | 原因 | 解法 |
|------|------|------|
| `ImportError: Unable to find zbar shared library` | libzbar 没找到（pyzbar 那句 `find_library('zbar')` 返回了 None） | 先 `sudo apt install -y libzbar0`（正路）；没 sudo 就确认 `vendor/lib/libzbar.so.0` 存在、且脚本里调用了 `zbar_bootstrap.ensure()` |
| `ModuleNotFoundError: No module named 'pyzbar'` | 翻译官没装 | `pip install pyzbar`（本机已装） |
| `ModuleNotFoundError: No module named 'cv2'` | OpenCV 没装 | `pip install opencv-python` |
| `RuntimeError: 找不到 …/vendor/lib/libzbar.so.0` | vendor 目录不在（比如复制项目时漏了） | 重新解包 deb，或改用系统安装 |
| `打不开摄像头 /dev/video0` | 被别的程序占用 / 设备没枚举好 / 权限不足 | 关掉占用程序；`ls -l /dev/video*` 看权限组；或第 06 课加 `--replay` |
| `[ X] Python 版本` | Python < 3.8 | 用 3.8+（本机 3.11.16） |

> **批注：为什么脚本里到处都有 `sys.path.insert(0, HERE)`？**
> 因为 `zbar_bootstrap.py` 在 `code/` 目录里，而你从根目录运行脚本时，
> Python 默认只在"当前目录"和"标准库"里找模块，找不到 `code/` 里的东西。
> `sys.path.insert(0, HERE)` 就是**临时把 `code/` 加进搜索路径**。
> 这是一种"自杀式补丁"——只在本进程有效，不会真的改系统配置，很安全。

## 7. 自测题

1. `pip install pyzbar` 成功，为什么还会报 "Unable to find zbar shared library"？

<details>
<summary>参考答案</summary>

1. 因为 pip 只装了 Python 包装（翻译官），zbar 本体是 C 库，要用 apt 装。

</details>

2. `LD_LIBRARY_PATH` 为什么对 `ctypes.util.find_library` 无效？

<details>
<summary>参考答案</summary>

2. `find_library` 查的是 `ldconfig -p` 缓存和 `gcc -lzbar` 链接测试，不走动态链接器的
   `LD_LIBRARY_PATH` 搜索路径。

</details>

3. `zbar_bootstrap.ensure()` 里的 `RTLD_GLOBAL` 起什么作用？去掉会怎样？

<details>
<summary>参考答案</summary>

3. `RTLD_GLOBAL` 把库的符号放进全局符号表，后续加载的模块（pyzbar）才能解析到
   zbar 的函数。去掉后符号不共享，pyzbar 仍可能找不到符号。

</details>

4. 如果 `zbarimg` 能读出图，但 Python 读不出，你应该先怀疑哪一端？

<details>
<summary>参考答案</summary>

4. 先怀疑 Python 这一端：bootstrap 有没有调用、路径对不对、pyzbar 版本。

</details>

5. 为什么体检脚本要试 `/dev/video0`~`/dev/video3` 而不是只试 0？

<details>
<summary>参考答案</summary>

5. 一个物理摄像头常会注册多个 `/dev/videoN` 节点（取流/元数据），而且不同节点能力和
   分辨率不同；不试一遍不知道哪个能真正出画面。

</details>

6. 你在一台装了系统 libzbar 的机器上，怎么验证 `vendor/` 那条兜底路真的能用？

<details>
<summary>参考答案</summary>

6. 把 `ctypes.util.find_library` 猴补丁成永远返回 `None`，再调 `zbar_bootstrap.ensure()`
   —— 它必须返回 `"bundled"` 并且还能读出码（见 5.5 节，本机实测通过）。

</details>

## 8. 小结

- 读码是**四人合作**：Python（皮）+ 数值图像库（料）+ libzbar（骨）+ pyzbar（翻译官）
- `pip` 管不到 C 库；**"装成功"≠"能跑"**，所以要体检
- zbar 本体两条路：**apt 装系统库**（正路，本机现状）/ **下载 deb → 解压 → 手动加载 + 猴补丁**（没 sudo 时的兜底），`bootstrap` 会自动二选一
- `zbarimg` 是你的**交叉验证工具**：它读得出 → 问题在 Python 侧
- 身体检查的逻辑（`check(name, fn, hint)`）就是后面读码流水线的雏形
