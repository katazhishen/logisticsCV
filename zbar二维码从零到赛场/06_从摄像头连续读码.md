## 1. 本课要解决的问题

前几课你读的都是**磁盘上的图片文件**。机器人拿到的是**摄像头画面**，差别很大：

| 项目 | 图片文件 | 摄像头画面 |
|------|---------|-----------|
| 数据形态 | PIL 的 `Image` 对象 | **numpy 数组（BGR 三通道）** |
| 数量 | 一张，想读几次读几次 | **每秒 30 帧，每帧只有一次机会** |
| 出错 | 文件不存在 → 报错 | **设备被占用/没插好 → 可能直接打不开** |
| 可复现性 | 完美（同一张图结果永远一样） | **差（光照、抖动、对焦每次不同）** |

所以本课要写的东西，不是"再读一次码"，而是**把读码嵌进一个循环里，并且算清楚它的时间账**。

### 为什么要有"回放模式"这种奇怪的东西？

因为**算法的调试必须可复现**。

真摄像头一秒钟给你 30 张**每次都不一样**的画面。你改了一行预处理代码，
命中率从 80% 变成 70% —— 是代码变差了？还是今天光线变了？**你无法判断。**

回放模式把这 60 帧**冻住**：同样的输入，跑两次结果必须一模一样。
于是"命中率 50%"这个数字才有意义 —— **它变成了可以优化、可以对比的指标**。

> **这条经验在赛场上同样适用**：
> 把调试时的摄像头画面**录下来**（哪怕只是存成图片序列），
> 之后所有调参都在录制数据上做，最后再去实车验证。
> 否则你会陷入"改了不知道有没有变好"的死循环。

## 3. 关键代码 1：一帧 BGR 图怎么交给 zbar

```python
def decode_frame(frame_bgr):                             # 一帧 BGR 图进，一串码出来
    """输入一帧 BGR 图，返回 pyzbar 的结果列表。"""
    gray = cv2.cvtColor(frame_bgr, cv2.COLOR_BGR2GRAY)   # 转灰度：zbar 只吃黑白，彩色添乱
    return decode(gray)                                  # 交给 zbar 找码，找不到是空列表
```

**为什么必须转灰度？** 两个理由：

1. **zbar 只需要黑白信息**。二维码的每一位不是黑就是白，彩色信息完全是浪费。
2. **快**。三通道转单通道，`decode` 处理的数据量直接降到 1/3。

> **批注：为什么不用 `cv2.imread(path, 0)` 直接读灰度？**
> 因为摄像头给的就是三通道 BGR，你没有"读文件时顺便转灰度"这个选项。
> **从摄像头来的数据，永远要自己转。**

> **批注：BGR 还是 RGB？**
> OpenCV 的默认顺序是 **BGR**（蓝绿红），而 PIL/matplotlib 是 RGB。
> **转灰度时这个顺序不影响结果**（三个通道加权求和，权重不同但都能算灰度），
> 但如果你想在画面上画彩色框，颜色会**红蓝互换**。
> 本教程统一用 `cv2.imshow` 看，所以直接写 BGR 的 `(0, 255, 0)`（绿）没问题。

### 顺手写一个"把结果画在画面上"的函数

```python
def draw_results(frame_bgr, results):                          # 调试用：把码框和内容画回画面
    for r in results:                                          # 一个 r 就是一个读出来的码
        # 四角转 int32 数组，传 Python 列表会报错
        pts = np.array([[p.x, p.y] for p in r.polygon], dtype=np.int32)
        cv2.polylines(frame_bgr, [pts], True, (0, 255, 0), 2)  # 沿四角画绿框，True 表示首尾闭合
        text = r.data.decode("utf-8", "replace")               # 字节转字符串，坏字符替换掉不炸
        x, y = r.rect.left, r.rect.top                         # 外接框左上角，文字贴着它摆
        # 文字在框上方 8px；y-8 会变负数，兜底压到 12
        cv2.putText(frame_bgr, text, (x, max(y - 8, 12)),
                    cv2.FONT_HERSHEY_SIMPLEX, 0.6, (0, 255, 0), 2)  # 字体、字号 0.6、绿色、线宽 2
    return frame_bgr                                           # 原地改的，返回同一块画面
```

> **为什么要 `max(y - 8, 12)`？**
> 因为码可能在画面最顶上，`y-8` 会变成负数，文字就画到画面外面去了（看不见）。
> **这种"边界兜底"是调试可视化的常见需求** —— 你总会在最坏的位置遇到它。

> **注意 `polylines` 要的是 `np.int32` 的 `(N,1,2)` 或 `(N,2)` 数组**。
> 直接传 `[[p.x, p.y] for p in ...]` 的 Python 列表在某些 OpenCV 版本上会报错。
> **`np.array(..., dtype=np.int32)` 是必须的。**

## 4. 关键代码 2：摄像头打不开怎么办

```python
class CameraSource:                                            # 摄像头输入源：对外只暴露 read()
    def __init__(self, index=0, width=640, height=480):        # 默认 /dev/video0，分辨率先按 640×480
        self.cap = cv2.VideoCapture(index)                     # 打开设备节点，此刻还没确认成功
        if not self.cap.isOpened():                            # 必须检查：否则后面拿到 None 才炸
            raise RuntimeError(f"打不开摄像头 /dev/video{index}")    # 抛给上层，让它决定降级还是重试
        # 设置分辨率只是"请求"，摄像头可能不给，所以要读回来看看
        self.cap.set(cv2.CAP_PROP_FRAME_WIDTH, width)          # 请求宽度，驱动有权无视
        self.cap.set(cv2.CAP_PROP_FRAME_HEIGHT, height)        # 请求高度，同上
        self.w = int(self.cap.get(cv2.CAP_PROP_FRAME_WIDTH))   # 读回真实宽度，别信请求值
        self.h = int(self.cap.get(cv2.CAP_PROP_FRAME_HEIGHT))  # 读回真实高度
```

**两个细节**：

1. **`isOpened()` 之后必须检查**，否则后面 `read()` 会返回 `(False, None)`，
   你的代码会拿一个 `None` 去做 `cvtColor`，报一句莫名其妙的错。
2. **`set()` 只是"请求"，不是"命令"**。摄像头的分辨率由硬件和驱动决定，
   你请求 1920×1080，它可能只给你 640×480。**所以必须 `get()` 读回来**。

### 自动降级：打不开就换回放

```python
def open_source(args):                                               # 选输入源：能用真机就用真机
    if getattr(args, "_replay_forced", False):                       # 上一帧刚失败过，别反复试摄像头
        return ReplaySource(os.path.join(ASSETS, "replay")), "回放模式"  # 直接给回放源
    if args.replay:                                                  # 用户显式要回放，结果可复现
        return ReplaySource(os.path.join(ASSETS, "replay")), "回放模式"  # 同样的 60 帧，每次结果一样
    # 先试真摄像头，打不开再降级
    try:
        # 正常路径：开摄像头，成功就返回
        return CameraSource(args.camera), f"摄像头 /dev/video{args.camera}"
    except RuntimeError as e:                                        # 打不开：被占用、没插好或索引错
        print(f"[提示] {e} —— 自动改用回放模式（assets/replay 里的图）。")           # 把降级原因打出来，别偷偷换源
        args._replay_forced = True                                   # 打标记，下一帧不再重试
        # 降级不崩：宁可读不到，也要跑完流程
        return ReplaySource(os.path.join(ASSETS, "replay")), "回放模式（摄像头不可用）"
```

> **这不是"偷懒"，这是工程习惯。**
> 你的机器人主程序里，摄像头开机失败**必须能降级或重试，不能整机卡死**。
> 想象一下：赛场上你的摄像头被碰松了，程序直接崩 —— 那 0 分。
> 一个"读不到码但我还能跑完流程"的机器人，比一个"摄像头一掉就死"的机器人强得多。

## 5. 实测账本：一帧到底花多少时间

这一节是本课的"硬货"。**所有数字都是本机实测的，不是估算。**

### 5.1 回放模式（640×480，60 帧）

```
           这一帧读出 0 个码。
           注意：这是『算法耗时』，不含摄像头本身的等待。

【第 2 步】进入循环：一帧一帧地读，读到就记住
           第 11 帧：第一次读到 → 156+123+516+231

==================================================================
【第 3 步】这一段跑完的统计
==================================================================
  处理帧数        : 60
  读到码的帧数    : 50（命中率 83.3%）
  第一次读到      : 第 11 帧
  最终内容        : 156+123+516+231
  总耗时          : 306.5 ms
  端到端帧率      : 195.8 帧/秒（fps）
  平均每帧解码    : 2.59 ms
```

### 5.2 真摄像头（/dev/video0，640×480，60 帧，画面里没有码）

```
【第 1 步】单帧解码耗时 9.35 ms  → 理论上每秒能处理 106.9 帧
           这一帧读出 0 个码。

  处理帧数        : 60
  读到码的帧数    : 0（命中率 0.0%）
  一次都没读到
  最终内容        : None
  总耗时          : 3199.3 ms
  端到端帧率      : 18.8 帧/秒（fps）
  平均每帧解码    : 8.22 ms
```

### 5.3 把这两组数字读成三条结论

**结论 1：算法本身很快，但"端到端"慢得多**

| 场景 | 单帧算法耗时 | 端到端每帧 | 差距来自 |
|------|-------------|-----------|---------|
| 回放 | 2.59 ~ 3.74 ms | 5.1 ms（306.5/60） | 读 PNG 文件的开销 |
| 真摄像头 | 8.22 ~ 9.35 ms | **53.3 ms**（3199.3/60） | **摄像头出图本身要 ~45ms** |

**真摄像头跑 60 帧要 3.2 秒，其中 2.7 秒在等摄像头。**
这就是为什么"端到端帧率 18.8"远低于"理论上 106.9" ——
**卡住你的不是算法，是摄像头。**

> **这对机器人意味着什么？**
> 想让主循环跑快，**优先降分辨率、提高曝光/亮度、缩短出图时间**，
> 而不是去优化解码算法（它只占 15% 的时间）。
> **优化要打在瓶颈上**，这是性能调优的第一原则。

**结论 2：真摄像头的画面比合成图难得多**

回放（合成图）：`decode` 平均 **2.59ms**，命中率 **83.3%**。
真摄像头：`decode` 平均 **8.22ms**，命中率 **0%**（因为画面里压根没有码）。

注意那个 **8.22 vs 2.59 的 3 倍差距**！同样的分辨率，为什么真摄像头慢 3 倍？
因为**真实画面里全是细节**：噪点、纹理、光影。zbar 要找定位图案，
合成图里它扫几行就找到了（或者立刻确认"没有"），
真实画面里它要扫遍每一个候选位置，找到最后才放弃。

> **这条非常重要**：`decode` 的耗时**和画面内容强相关** ——
> **找不到码的时候最慢**（要扫全图）。
> 所以在"画面里没码"的正常状态下，你的主循环会被拖得最慢。**做预算要按最坏情况算。**

**结论 3：前 10 帧读不出，是"模糊"造成的**

看回放数据：**第一次读到是第 11 帧**，前 10 帧一次都没读到。
这不是 bug —— `assets/replay/` 的素材是**故意**这样造的：
前 10 帧模糊度从重到轻渐变（模拟"车正在移动、摄像头还没对焦稳"）。

**第 07 课的任务，就是把这 10 帧救回来。** 到时候你会看到：

```
命中率 83.3%  →  接近 100%
```

这就是"预处理"要解决的**真实问题**，不是教科书上为了考试而编的题。

## 6. 关键代码 3：主循环（注意三个细节）

> **🚫 片段（不能单独运行）** —— src 是第 3 步创建的输入源对象，单独复制会报 `NameError: name 'src' is not defined`。完整可运行版：`python code/lesson06_camera.py`。

```python
# ═══ 1. 计数器：帧号、命中数、解码耗时 ═══
first_hit = None          # 第一次读到的帧号
final_text = None         # 记住第一次成功的，别被空帧覆盖
n = 0                    # 已处理的帧数
hits = 0                 # 读到码的帧数
decode_time_total = 0.0  # 只累计解码，不含等帧

# ═══ 2. 主循环：一帧一帧读，读到就记住 ═══
while True:                           # 帧数不确定，只能一直读
    frame = src.read()                # 回放和摄像头共用这个接口
    if frame is None:                 # ← 细节 1：None 表示"流结束"
        break                         # 用 None 判结束，两种来源都行
    n += 1                            # 帧号加一，对应前面的第 N 帧

    # ═══ 3. 解码计时，只量算法本身 ═══
    t0 = time.perf_counter()          # 开始打点
    results = decode_frame(frame)     # 真正的活：转灰度 + zbar 找码
    decode_time_total += time.perf_counter() - t0   # ← 细节 2：只累计解码耗时

    if results:                       # 空列表说明这帧没读到
        hits += 1                     # 记一次命中
        if final_text is None:        # ← 细节 3：只记第一次成功
            # 字节转文本，坏字符替换；后面误读盖不掉
            final_text = results[0].data.decode("utf-8", "replace")
            first_hit = n             # 回放模式里这个 n 是 11
            print(f"           第 {n} 帧：第一次读到 → {final_text}")  # 与参考结果同一格式
```

### 细节 1：用 `None` 表示"流结束"

`CameraSource.read()` 在取帧失败时返回 `None`；`ReplaySource.read()` 在播完所有图后返回 `None`。
**统一用 `None` 表示结束**，主循环就能同时兼容两种来源 —— 这叫**接口统一**。

### 细节 2：为什么要单独累计解码耗时？

因为"端到端帧率"和"算法耗时"是**两个不同的指标**：

- 端到端帧率（18.8 fps）告诉你**整个系统**多快
- 平均解码耗时（8.22ms）告诉你**算法**多快

两者差得远 → 瓶颈在别处（摄像头）。
**不分开测，你永远不知道该优化哪儿。**

### 细节 3：为什么只记第一次成功的内容？

因为后面某一帧可能**误读**（噪点凑巧被解成另一个字符串）。
如果你的逻辑是"每帧覆盖"，最后一帧的误读会污染结果。

> **正确做法在第 12 课进阶 B**：滑动窗口投票。
> 现在先用"第一次"这个最朴素的策略（赛场上读一次任务码就够了）。

### 一个真实踩过的坑：`--bench` 把解码跳过了

早期版本里主循环是这么写的：

> **🚫 片段（不能单独运行）** —— args 是 argparse 解析出来的命令行参数，单独复制会报 `NameError: name 'args' is not defined`。完整可运行版：`python code/lesson06_camera.py`。

```python
# 错误示范：--bench 时把解码整个跳过
# 后果：测出来 404 fps，其实是空转
results = decode_frame(frame) if not args.bench else []     # ← 错的
```

测出来 **404 fps**，看起来性能无敌。**但那是空循环的速度** ——
`--bench` 把解码整个跳过了，测的是"什么都不干有多快"。

改成：

> **🚫 片段（不能单独运行）** —— 它调用本课第 2 步定义的 decode_frame()，单独复制会报 `NameError: name 'decode_frame' is not defined`。完整可运行版：`python code/lesson06_camera.py`。

```python
# 注意：--bench 只是"不弹窗预览"，解码照做
results = decode_frame(frame)  # 解码照做，测的才是真实速度
```

再测就是 **195.8 fps**。

> **这个坑非常典型**：**测速代码本身把被测对象跳过了**。
> 记住这句老话：**"先确认你在测什么，再相信测出来的数。"**

### 练习 6-A：只跑前 20 帧，命中率会变成多少？

用 `--replay --bench --frames 20`，预测命中率，再验证。为什么？

<details>
<summary>参考答案</summary>

```bash
python code/lesson06_camera.py --replay --bench --frames 20
```

参考结果：

```
  处理帧数        : 20
  读到码的帧数    : 10（命中率 50.0%）
  第一次读到      : 第 11 帧
```

**为什么正好 50%？** 因为 20 帧里，第 1~10 帧是模糊的（读不出），第 11~20 帧清晰（都读出）。
**10/20 = 50%。**

> **这个练习教了一件重要的事**：
> **命中率这个指标会被"窗口长度"操纵。**
> 如果你只跑前 5 帧，命中率是 0%；只跑后 10 帧，命中率是 100%。
> **报命中率时一定要带上样本量和条件**，否则就是耍流氓。

</details>

### 练习 6-C：连续两帧一致才认账

改主循环：只有**连续 2 帧读到同一内容**才认，输出"第几帧确认"。
比较和"第一次读到"的差别，说说哪种更可靠、代价是什么。

<details>
<summary>参考答案</summary>

> **🚫 片段（不能单独运行）** —— src 是第 3 步创建的输入源对象，单独复制会报 `NameError: name 'src' is not defined`。完整可运行版：`python code/lesson06_camera.py`。

```python
# ═══ 1. 记录连续读到同一内容 ═══
streak_text = None                                  # 上一次读到的内容
streak_n = 0                                        # 已经连续读到几次
confirmed_at = None                                 # 确认时的帧号

# ═══ 2. 主循环：内容变了就重新数 ═══
while True:                                         # 一直读，直到流结束
    frame = src.read()                              # 拿下一帧
    if frame is None:                               # None 表示没帧了
        break                                       # 退出循环
    n += 1                                          # 帧号加一
    results = decode_frame(frame)                   # 解码这一帧
    if results:                                     # 读到了才算一次
        # 同一帧的文字转成字符串，坏字符替换
        text = results[0].data.decode("utf-8", "replace")
        if text == streak_text:                     # 和上次内容一样
            streak_n += 1                           # 连续计数加一
        else:                                       # 内容变了，或第一次读到
            streak_text, streak_n = text, 1         # 从 1 重新数
        if streak_n >= 2 and confirmed_at is None:  # 连续 2 帧一致才认账
            confirmed_at = n                        # 记下确认的帧号
            print(f"第 {n} 帧：连续 2 帧一致，确认 → {text}")         # 回放里是第 12 帧
    else:                                           # 这一帧没读到
        streak_text, streak_n = None, 0      # 一旦没读到，计数清零
```

参考结果（回放模式）：

```
第 12 帧：连续 2 帧一致，确认 → 156+123+516+231
```

**对比**：

| 策略 | 首次可用帧 | 抗误读 | 代价 |
|------|-----------|--------|------|
| 第一次读到就认 | 第 11 帧 | ❌ 一帧误读就全错 | 0 |
| 连续 2 帧一致 | 第 12 帧 | ✅ 基本免疫单帧误读 | **晚 1 帧**（约 33ms@30fps） |

> **这笔交易极其划算**：花 33 毫秒，换来"不会因为一帧噪点把任务码读错"。
> **赛场上读错任务码 = 全盘皆错**，比晚 33ms 严重得多。
> 第 10 课会把这个逻辑做成 `RobustReader(confirm=2)` 的参数。

</details>

### 练习 6-D：验证"没码时更慢"

在回放模式下，分别测 `frame_000.png`（模糊、读不出）和 `frame_030.png`（清晰、有码）
的 `decode()` 耗时（各跑 20 次取平均）。证实"读不出时更慢"。

<details>
<summary>参考答案</summary>

```python
# ══════ 环境准备（每个示例都一样，照抄，不用改任何东西）══════
import os, sys
ROOT = "/home/kata/Desktop/logisticsCV/zbar二维码从零到赛场"   # 教程根目录
os.chdir(ROOT)                                    # 让示例里的 "assets/xxx" 找得到
sys.path.insert(0, os.path.join(ROOT, "code"))    # 让 import zbar_bootstrap 找得到
import zbar_bootstrap
zbar_bootstrap.ensure()                           # 确认 zbar 已就绪（第 02 课验证过）
from PIL import Image
from pyzbar.pyzbar import decode
# ══════════════════════════════════════════════════════════

import time                                          # 只为 perf_counter 计时
import cv2                                           # 读图、转灰度
from pyzbar.pyzbar import decode                     # 找码入口

for name in ("frame_000.png", "frame_030.png"):      # 一张模糊、一张清晰
    # 读图并转灰度；两张互不影响
    gray = cv2.cvtColor(cv2.imread(f"assets/replay/{name}"), cv2.COLOR_BGR2GRAY)
    decode(gray)                                    # 预热一次，别让第一次的缓存影响
    t0 = time.perf_counter()                         # 开始计时
    for _ in range(20):                              # 重复 20 次取平均
        r = decode(gray)                             # 只测 decode 本身
    t = (time.perf_counter() - t0) / 20 * 1000       # 换算成毫秒
    print(f"{name}  平均 {t:5.2f} ms  读出 {len(r)} 个")  # 与下面的参考结果对照
```

参考结果（本机实测）：

```
frame_000.png  平均  2.60 ms  读出 0 个
frame_030.png  平均 12.68 ms  读出 1 个
```

> **⚠️ 注意：结果和我在第 5 节说的"没码时更慢"是反的！**
> 实测是"**有码时更慢**"（12.68ms vs 2.60ms）。
>
> 我得诚实纠正自己：
> - 模糊图（frame_000）**看起来就"不像有码"**，zbar 快速放弃 → 2.6ms
> - 清晰图（frame_030）**真的找到了码**，要走完"定位 → 采样 → 纠错 → 解码"全流程 → 12.68ms
>
> **正确的结论是**：`decode` 的耗时取决于"图里有多少像码的东西"。
> 全白/全糊的图最便宜，"有一点点像"的图最贵（要找半天最后放弃），
> "清清楚楚有码"的图走完整流程，也贵。
> **做时间预算时按"最贵"算：~13ms/帧（640×480、清晰有码）。**

</details>

### 练习 6-E：摄像头真的不是瓶颈吗？

用真摄像头跑 `--frames 30`，拿到"端到端每帧 ms"和"平均解码 ms"，
算出"摄像头出图"占了多少毫秒。

<details>
<summary>参考答案</summary>

```bash
python code/lesson06_camera.py --bench --frames 30
```

参考结果（本机实测，真摄像头 640×480，画面里无码）：

```
  处理帧数        : 60 → 换成 --frames 30 就是 30
  平均每帧解码    : 8.22 ms
  端到端帧率      : 18.8 帧/秒
```

算一下：

```
端到端每帧 = 1000 / 18.8 = 53.2 ms
其中解码   = 8.22 ms
摄像头出图 = 53.2 - 8.22 ≈ 45.0 ms
```

**摄像头占了 85% 的时间。**

> **这就是本课最实用的一条**：
> 与其花三天优化解码算法（最多省下几毫秒），
> 不如把分辨率从 1280×720 降到 640×480，或者把曝光时间调短 —— **立刻省 20ms**。

</details>

## 8. 常见错误

| 报错 / 现象 | 原因 | 解法 |
|------------|------|------|
| 程序一直不退出 | 真摄像头 + 没给 `--frames`（无限循环） | 加 `--frames N`，或 Ctrl+C |
| `can't open camera by index` | 被占用 / 没 release / 索引不对 | 关掉占用程序；`cap.release()`；试 `--camera 3` |
| `cv2.imshow` 报 `The function is not implemented` | 无图形界面（服务器/SSH） | 别用 `--show`，用 `--bench` |
| `TypeError: Expected Ptr<cv::UMat> for argument 'pts'` | `polylines` 的点没转 `np.int32` | `np.array(..., dtype=np.int32)` |
| `error: (-215) scn == 3 || scn == 4` | 把单通道图喂给了要三通道的函数 | 检查 `frame.shape`，别混用灰度/BGR |
| 端到端帧率忽高忽低 | USB 带宽波动 / 自动曝光在调整 | 固定分辨率与曝光；或用录制数据调参 |

## 9. 自测题

1. 摄像头画面为什么必须 `cvtColor` 转灰度？不转会怎样？

   <details>
   <summary>参考答案</summary>

   zbar 只需要黑白信息；三通道是 3 倍数据量。不转灰度 pyzbar 也能接受彩色数组，但更慢，而且 OpenCV 后续处理需要统一格式。

   </details>

2. `cap.set(CAP_PROP_FRAME_WIDTH, 1920)` 之后，`cap.get(...)` 一定返回 1920 吗？为什么？

   <details>
   <summary>参考答案</summary>

   不一定。`set` 只是"请求"，实际分辨率由摄像头/驱动决定，必须 `get` 回来确认（本机 video1/video2 是 360×360）。

   </details>

3. 回放模式存在的意义是什么？它比真摄像头好在哪、差在哪？

   <details>
   <summary>参考答案</summary>

   意义是**可复现**：同样输入必得同样输出，才能把"命中率"当可对比的指标。差在不是真实现场（无噪声/无抖动/无光照变化）。

   </details>

4. 本机上"端到端 53.2ms、解码 8.22ms"说明瓶颈在哪？你会怎么优化？

   <details>
   <summary>参考答案</summary>

   瓶颈在摄像头出图（约 45ms，占 85%）。优化方向：降分辨率、缩短曝光、换更快接口，而不是优化解码。

   </details>

5. 为什么 `--bench` 早期版本测出 404 fps 是错的？

   <details>
   <summary>参考答案</summary>

   因为 `--bench` 把 `decode_frame` 整个跳过了，测的是空循环速度，与被测对象无关。

   </details>

6. "命中率 83.3%"这个数字，为什么必须和"跑了 60 帧"一起说？

   <details>
   <summary>参考答案</summary>

   命中率随样本窗口剧烈变化（前 5 帧 0%、后 10 帧 100%），脱离样本量的命中率没有意义。

   </details>

## 10. 小结

| 你学到的 | 一句话 |
|---------|--------|
| 数据形态 | 摄像头给 BGR numpy 数组，`cvtColor` 转灰度再 `decode` |
| 接口统一 | 两种来源都用 `read() → frame or None`，主循环只写一份 |
| 降级 | 摄像头打不开 → 自动回放，**不崩** |
| `set` 是请求 | 分辨率必须 `get` 回来确认 |
| 时间账 | 真机 53.2ms/帧，其中 45ms 在等摄像头 → **瓶颈不在算法** |
| `decode` 耗时 | 与内容强相关：模糊图 2.6ms、清晰有码 12.7ms；预算按 ~13ms |
| 命中率 | 前 10 帧全灭（模糊）→ 第 07 课要救的就是它们 |
| 测速纪律 | 先确认测的是什么，再相信数字（404fps 的教训） |
